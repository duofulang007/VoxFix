## 二、手机实现（本轮第一段）

平台事实：Android 的 `MediaProjection` 只能整屏采集，没有区域参数，也没有"排除某个窗口"的公开能力；系统声音只能通过 `AudioPlaybackCapture` 录到**允许被捕获**的应用。

实现选择与差异：

| 项 | 手机实现 | 与原版差异 |
| --- | --- | --- |
| 区域录制 | `VirtualDisplay` 全屏 → `SurfaceTexture` → EGL 按选区裁剪/缩放 → `MediaCodec` 输入 Surface | 原版后端直接按区域采集；手机在 GL 阶段裁剪，裁切范围与截图选区同一坐标系 |
| 输出格式 | 第一段只做 MP4（H.264 + AAC） | GIF/APNG/WebP 动画格式待第二段；动画格式本来也没有音频 |
| 帧率/清晰度/质量 | 读取设置（默认 30fps、1080p、质量 80），按选区尺寸等比缩放到清晰度上限 | 无 h265/预设选择；硬件编码器由系统选择 |
| 音频 | 麦克风或系统内录二选一（默认系统内录，与原版默认一致）；系统内录录不到禁止捕获的应用时降级为静音轨并在结束时提示 | 原版可两路混音/分轨；手机第一段不做混音 |
| 暂停/恢复 | 停止送帧、停止送 PCM，PTS 扣除暂停时长，容器时间轴连续 | 行为对齐原版 |
| 录制前设置阶段 | 截图工具条点录制 → 关闭截图界面 → 打开"蓝框 + 控制条"的设置阶段：框可移动/拉边缩放，控制条为「开始 / 00:00:00 / 关闭 / 麦克 / 设置」，点开始才申请授权并进入倒计时/录制 | 原版无授权步骤；`ScreenRecordingAreaWindow` 的绘制工具与实时特效预览手机不做；原版 Idle 默认展开导出设置面板，手机默认收起、点齿轮展开单行参数条 |
| 设置行 | 设置阶段把导出参数压成单行横向标签（格式 / 清晰度 / 帧率 / 质量 / 声音 / 延迟 / 文件夹），超宽横向滚动；点标签循环取值并立即生效 | 原版同为单行 `QHBoxLayout`（下拉/取色器/图标+值），桌面宽度放得下；手机为触屏加了滚动，竖排六行的第一版会占掉约半屏，已废弃 |
| 设置阶段选区编辑 | `ScreenRecordingSetupView` 8 个手柄 + 20dp 命中带，角/边缩放按 `resizegeometry.h` 的 `dragGeometry`/`anchoredRect` 移植（拖过对边会换边而不翻转），框内拖动整体移动；最小 32dp；选区夹在屏幕内 | 原版手柄靠鼠标光标提示、命中带 6 逻辑像素、最小 10 物理像素、窗口允许悬出屏幕——触屏与裁切实现都需要更宽的带与更严的夹取 |
| 控制栏 | 选区外浮条：设置阶段「开始 / 时长 / 关闭 / 麦克 / 设置」，录制中「时长 / 暂停 / 完成 / 取消 / 麦克」，设置仅在设置阶段可用 | 原版工具条含绘制工具，手机第一段不含录制中标注 |
| 延迟录制 | 0/3/5/10 秒，点开始先倒计时（条内显示秒数），倒计时结束才起编码并开始计时 | 原版倒计时是选区中央 88px 圆形指示器；手机放在控制条内 |
| 成品落地 | 保存到 `Movies/VoxFix/`（MediaStore），Toast 提示；控制条可再打开成品 | Android 剪贴板不支持视频文件，原版"复制到剪贴板"无对应能力，改为保存后即可在相册查看 |
| 光标/键盘特效 | 不做：手机无鼠标、无外接键盘浮显语义 | 原版桌面专属 |
| 延迟录制 | 0/3/5/10 秒，点开始先倒计时（条内显示秒数），倒计时结束才起编码并开始计时 | 原版倒计时是选区中央 88px 圆形指示器；手机放在控制条内 |
| 旋转 | 录制中检测到屏幕旋转即收尾保存并提示；设置阶段旋转则取消设置并提示重选 | 原版区域固定不随屏转 |

保存与命名：`VoxFix 录屏 yyyy-MM-dd HH-mm-ss.mp4`，与截图命名风格一致；单文件失败时保留临时文件并提示，不静默丢弃。

## 六、第二轮：导出设置、延迟倒计时、打开录制文件夹（2026-11-06）

原版录制工具条的导出参数行（`screenshottoolpalette.cpp:5944-6192`）和延迟编辑器（`6110-6130`）已按手机形态落地：

| 子项 | 原版 | 手机实现 | 差异 |
| --- | --- | --- | --- |
| 参数入口 | 工具条常驻一行：格式、轨迹色、点击色、光标、按键、延迟、设置 | 控制条「设置」展开六行面板 | 手机屏窄，改为展开面板；录中禁用 |
| 格式 | MP4/GIF/APNG/WebP | 四选一，点按循环 | 见第十节（本轮补齐） |
| 清晰度 | 4k/2k/1080p/720p/480p | 同 5 档，点按循环 | 无滚轮，改为点按 |
| 帧率 | 任意整数（默认 30） | 15/24/30/60 四档 | 触屏循环取值，减少误调 |
| 质量 | 0–100 连续，默认 80 | 40/60/80/100 四档 | 同上；码率换算沿用 `bitrate()` |
| 声音 | 麦克风/系统声独立开关 + 分轨 | 麦克风→系统声音→静音三态互斥 | 不做混音/分轨 |
| 延迟 | `startDelaySeconds`，选区窗口倒计时 | 0/3/5/10 秒；投影就绪后控制条倒数，可取消；倒数结束才创建编码器 | 倒计时期间系统「屏幕共享」已生效，无法提前隐藏 |
| 打开录制文件夹 | `openScreenRecordingFolder` | 面板底部「打开录制文件夹」，打开相册视频列表；无处理应用时提示 | Android 无文件夹浏览器 |

参数改动只在空闲状态可编辑，录制中禁用「设置」；面板值写入 `voxfix-recording` 偏好，下次录屏生效（控制条会提示「已记住，下次录屏生效」）。投影授权后的倒计时期间旋转屏幕会取消本次录制并提示重新选区域。

已知可用性问题：录屏图标在默认工具栏布局里位于末段（默认 21 个可点项，屏上只显示两行约 11 个），有选区时会被挤出可视区，需要在工具栏内**向上滚动**才能露出（`ScreenshotToolbarPanel` 的 ScrollView，滚到底后最后一行是贴图／分享／长截屏／录屏）。原版桌面宽度足够，这属于手机小屏适配的既有行为。设备断言与 JVM 不覆盖该布局，真机走查时优先确认能否滚到。

## 七、录制区域边框（2026-11-06，用户反馈「看不到在录哪一块」）

## 八、红线入镜与画质修复（2026-11-06，用户反馈）

用户反馈三件事：录制范围里出现一条红横线、疑似把选区框录了进去；「屏幕共享」后不少内容录不到、发虚。

### 8.1 红线入镜

根因是边框与选区的间隙只有 1dp（约 3px），而缩小采样与编码器对奇数尺寸的 1 像素扩张都可能把边界外像素带进来。修复两层：

1. `ScreenRecordingAreaView` 的间隙从 1dp 改为 3dp（描边外移 4dp），红框离录制区足够远；
2. `cropFraction` 新增 `insetPx`，录制时向选区内部再收 2px，吸收任何边缘混合与对齐误差。

设备断言随之更新为 `strokeCentre = region.left - 4dp`，结果 `SCREENSHOT_RECORDING_AREA_PASS:stroke=109px:inside=clear`。

### 8.2 码率与清晰度

- 旧码率用自拟的 `像素×帧率×0.07×质量` 系数，1080p30 质量 80 只有约 4.3 Mbps，动态画面发虚、块效应明显。现按上游 `snow-crates/.../video_quality.rs::smart_quality_bitrate_kbps` 逐行移植：1080p30 参考阶梯质量 80 约 14 Mbps、质量 100 约 18 Mbps，按像素数 `^0.92`、帧率 `^0.85` 缩放，并有小区域下限。`ScreenRecordingGeometryTest` 同步改为按该公式断言。
- 清晰度默认从 1080p 改为 2K。原版桌面屏幕一般不超过 1920 高，而手机竖屏是 1080×2400；1080p 档会把整屏录制缩到 864×1920（丢 20% 分辨率）。2K 档在 K60 上保持原生像素，更大区域才缩放。这是手机侧与上游默认值的差异。
- 「部分内容录不到」若指某些应用画面黑屏或模糊，那是该窗口设置了 `FLAG_SECURE`（支付、密码、部分视频与系统界面），Android 在 MediaProjection 层强制屏蔽，任何录屏应用都一样，无法通过代码绕过；若指包含这些窗口的整屏，其余区域仍正常录制。

主包 sha256 `7b596065c1d012631f8be0025cfc53e32faeb52e144d0bf3d49eedd78402eb3a`（设备一致），JVM 380 项零失败，`screenshot-recording` 仍通过，系统状态一致。

## 十、动画格式导出：GIF / APNG / WebP（2026-11-06 第六轮）

原版把 GIF/APNG/WebP 全部交给 FFmpeg（`streaming.rs` 只额外设置 `loop`/`plays`），Android 没有公开的动画图编码器，手机侧必须自己写容器。

### 10.1 上游取值（全部来自固定提交，不是推断）

| 项 | 上游事实 | 出处 |
| --- | --- | --- |
| 动画清晰度 | 默认 `720p`，候选只有 `1080p / 720p / 480p`（与 MP4 的 5 档不同） | `storage/configurationschema.cpp:418-422` |
| 动画帧率 | 默认 `10`，候选 `5 / 10 / 15 / 24`；≤0 时回落 10 | 同上 `423-424`、`screenrecordingcontroller.cpp:77-79` |
| 循环 | `loop_animated_images` 默认 `true` | 同上 `425-426` |
| 循环落盘 | GIF `loop=0`（无限）/`-1`（不写扩展）；APNG `plays=0`/`1`；WebP `loop=0`/`1` | `streaming.rs:763-785` |
| 音频 | `audioSupported = outputFormat == "mp4"`，动画格式无音轨 | `screenrecordingcontroller.cpp:815` |
| 动画参数独立 | 非 MP4 走 `animated_clarity` + `animated_frame_rate`，不读 MP4 的清晰度/帧率 | `screenrecordingcontroller.cpp:121-133` |

### 10.2 手机实现

| 文件 | 职责 |
| --- | --- |
| `ScreenAnimationExport.kt` | 纯 Kotlin：GIF 调色板 + LZW、APNG 块流、WebP 动画容器 |
| `ScreenAnimationWriter.kt` | 单帧队列 + 编码线程，按格式分派；WebP 用平台静态编码器出位流 |
| `ScreenRecorder.kt` | 动画格式改走 EGL **pbuffer** + `glReadPixels`（无编码器 Surface），行序翻转后交给写出器 |
| `ScreenRecordingSettings.kt` | `animatedClarity` / `animatedFrameRate` / `loopAnimated` 持久化；按格式返回生效值与候选集 |
| `ScreenRecordingControl.kt` | 「格式」四选一点按循环；动画下隐藏「声音」与（GIF/APNG 的）「质量」，新增「循环」 |
| `ScreenRecordingLibrary.kt` | GIF/APNG/WebP 进 `Images` 集合的 `Pictures/VoxFix`，MIME 按扩展名；打开与相册入口同型 |

关键实现点：

- **GIF 调色板**逐行移植 `snow-recording-export/src/gif_palette.rs`：32³ 直方图、255 色中位切分（按 人口×色域 加权）、RMS 8 / 单格 32 两级重建阈值、8×8 Bayer（等价 `bayer_scale=3`）只对量化误差抖动、精确色不抖动。LZW 自写（清空码 256 / 结束码 257，9→12 位宽随字典增长）。
- **APNG**：`IHDR` + `acTL`（帧数先写 0，收尾回填并重算 CRC）+ 每帧 `fcTL` 与其独立的 zlib 流；首帧 `IDAT`，后续 `fdAT`。
- **WebP**：不引入 VP8 编码器。平台 `Bitmap.compress(WEBP_LOSSY)` 产出的静态 WebP 里取出 `VP8 `/`VP8L`（以及可能的 `ALPH`）位流，按 `VP8X / ANIM / ANMF` 组装动画容器，收尾回填 RIFF 长度（小端）。
- **帧率与丢帧**：采集线程只负责渲染 + 回读，编码在独立线程；只有一个待编码槽位，来不及就丢当前帧，下一帧的延时按**真实时间差**写入（10–65535 ms 夹取），因此丢帧只会让动画变慢而不是整体提速。
- **方向**：`glReadPixels` 自下而上，回读后按行翻转，成品方向与选区一致（`screenshot-recording-pipeline` 断言首行为 GL 上半部分颜色）。

### 10.3 与原版的差异（不得写成已复刻）

1. **GIF 不做帧间差分**：上游靠 FFmpeg `gifflags=3`（offset+transdiff）在调色板不变时只写变化区；手机每帧独立局部调色板 + 全帧 LZW，文件更大（实测 864×720×10fps 约 8.6 秒 2.84 MB）。
2. **延时按实际间隔**：上游是恒定 fps 的时间基；手机丢帧时下一帧延时变长，播放仍是真实时长。
3. **APNG 在 Android 上只显示首帧**：文件本身是合法 APNG（JDK ImageIO 可解 4 帧），但 Android 的 `ImageDecoder` 返回 `BitmapDrawable`（`animated=false`），相册/看图应用不会播放。这是平台解码能力差异，原版桌面播放器正常。
4. 动画格式不出音轨（与上游一致），设置里的「声音」自动隐藏、麦克风按钮禁用。

### 10.4 顺带修掉的真实缺陷：授权期间服务被重建

走查时发现「点开始 → 授权弹窗 → 之后什么都不发生」，日志里有一条 `RejectedExecutionException`（`ScreenTextService.launchRecorder`）导致进程崩溃。根因：**这台 ROM 在 `MediaProjectionPermissionActivity` 前置时会销毁并重建无障碍服务**，而录屏回调闭包绑在旧实例上。

修复：

- `ScreenshotProjection.request` 不再 `check(pending == null)` 崩溃，重复请求会丢弃陈旧的；新增 `abandonUnlessUiOpen()`：授权界面还开着时**保留**请求，只有已回到 App 的才丢弃。
- 回调改为路由到 `ScreenTextService.live`（`onServiceConnected` 赋值、`onDestroy` 清理），由当前存活实例执行 `beginRecording`。
- `launchRecorder` 的线程池投递加了拒绝兜底，服务已销毁时只记 `SCREEN_RECORD_WORKER_GONE` 并收尾，不再杀进程。
- 服务重建后控制条会重新创建（否则只有红框没有暂停/完成按钮）。

本轮改掉的缺陷（都属于"看起来在录、其实在丢"的类型）：

1. **动画帧率只有 4.4 fps**：根因不是编码慢（实测回读 39 ms、编码 27 ms），而是**静态画面下 VirtualDisplay 不产生新帧**，`onFrameAvailable` 根本不回调。改为按目标帧率用 `postAtTime` 固定节拍重复输出当前纹理；同时"做完再延时"会把 100 ms 变成 170 ms，必须用固定时间轴。丢帧时时间戳不推进，下一帧延时补上，播放速度不变。修好后三格式都稳定在 10.05 fps。
2. **APNG 体积/速度**：IHDR 从 RGBA 改为 truecolour(2)，并对每行在 None/Sub/Up 中按绝对值和择优（并列取 Up，重复行变成零串）。
3. **拒绝授权后永久卡死**：系统在授权弹窗前置时会销毁并重建无障碍服务，结果可能永远送不回来，`busy` 保持 true，之后每次录制都被 `RECORDING_SETUP_SKIPPED busy=true` 拦掉。现在授权活动在非 config change 的销毁里一律回收请求（`ScreenshotProjectionActivity.onDestroy`），并加了 `RECORDING_BUSY_STALE_RESET` 自愈。
4. **录制被服务重建"孤儿化"**：录制对象原先存在服务实例字段里，实例重建后控制条、旋转监听、停止入口全部指向旧实例，录制继续却无法停止。改为进程级持有（`sharedRecorder` + 区间/选项/起始时间），新实例 `onServiceConnected` 会 `RECORDING_ADOPTED` 接管并重建红框与控制条（计时按真实经过时间恢复）；`onDestroy` 从"取消并删除"改为"收尾保存"，避免数据静默丢失。

## 十一、录制中旋转收尾（2026-11-06 第八轮）

- **根因是两层，只改显示监听修不好**：
  1. `DisplayManager.DisplayListener.onDisplayChanged` 在这台 ROM 上从不回调（§10.7 实测）；
  2. 更要命的一层——授权时系统会重建无障碍服务，`watchRecordingRotation()` 只在旧实例的 `enterRecordingSetup` 里调用过，**接管录制的新实例根本没有旋转监听**，就算回调正常也不会收尾。证据：16:52 那次 `PROJECTION_KEPT`（旧实例销毁）后的 `RECORDING_LAUNCH` 来自新实例，转屏后日志一片空白，录制一直跑到 53.9 s 才手动停止。
- **上游依据**：`screenrecordingareawindow.cpp` 的选区固定在屏幕像素坐标、窗口只是覆盖层，录制区域不随屏幕旋转；手机上 VirtualDisplay 无法中途重裁，所以"旋转即收尾保存"是唯一正确映射。
- **实现（`ScreenTextService.kt` + `ScreenRecordingSettings.kt`）**：
  1. `currentRotation()` 读 `DisplayManager.getDisplay(DEFAULT_DISPLAY).rotation`；判定抽成纯函数 `ScreenRecordingGeometry.rotationSuperseded(baseline, current)`（任一侧为未知 `-1` 不算变化），配 JVM 断言。
  2. 三条触发：`onConfigurationChanged`（最早到）、400 ms 轮询 `rotationPoll`（真正生效的那条）、`adoptRunningRecording` 用进程级 `sharedRotation` 比对（服务重建期间转屏）。
  3. 轮询在 `beginRecording` 再武装一次——录制归属新实例，`enterRecordingSetup` 装的那份随旧实例销毁。
  4. 基线只在未知时取当前值，且 `sharedRotation` 优先，避免把"已经转过去的屏幕"当成新基线。
  5. 无会话时（`liveRecorder`、`recordingSetup` 都空）只更新基线不写日志——`onConfigurationChanged` 在录完之后仍会来。
  6. 收尾后控制条按新屏幕尺寸重新摆位，避免「已保存 / 查看」落在横屏视野外。
- **真机验收（K60 `6959dba1`）**：

  - 设置阶段旋转：16:57:53 进入设置，16:58:04 转屏 → `RECORDING_ROTATION_END rotation=1` + `RECORDING_SETUP_CANCELLED reason=屏幕已旋转，请重新选择录制区域`，随后可再次进入设置阶段。
  - 转回竖屏不再误报（基线收敛生效）；控制条「关闭」仍可收起设置阶段（`reason=已关闭录屏设置`）。

## 十二、GIF 帧间差分与体积（2026-11-06 第九轮）

- **上游依据**：FFmpeg 的 GIF 编码器默认 `gifflags = offsetting | transdiff`（`libavcodec/gif.c`：`gif_crop_opaque` 裁变化矩形、`honor_transparency` 把与上一帧相同的像素写成透明索引），而 Snow Shot 只在调色板与上一帧相同时保留这两个开关（`gif_palette.rs::GifDeltaState::prepare`：`palette == previous_palette ? 3 : 0`），并把 PAL8 的第 255 项留作透明色（`COLORS = 255`，`palette[255] = 0`）。
- **手机实现（`ScreenAnimationExport.kt::GifEncoder`）**：
  1. 帧头延后到第一帧写出——首帧调色板成为**全局色表**（256 项，第 255 项为透明占位）；调色板与全局表相同的帧不再写 768 字节局部色表，不同的帧照旧写局部表（对应 FFmpeg 的 `palette != NULL` 分支）。
  2. 调色板与**上一帧**相同时裁到变化区域：先裁相同的顶/底行，再在剩余行范围内裁相同的左右列（`gif_crop_opaque` 逐行移植）；完全相同的两帧收敛为 1×1。
  3. 该区域内与上一帧相同的像素改写为透明索引 255，GCE 打开透明标志、处置方式仍为「不处置」。
- **真机（K60）**：
  - 静态页 26.4 s：**262 帧 / 41,186 B = 157 B/帧**（首帧 622,080 px 整幅，其余 261 帧全差分，其中大量 1×1 空帧）；同画面的旧实现为 **82 帧 / 2,839,529 B = 34,628 B/帧**，即每帧体积约为原来的 **1/220**。
  - 含滑动的 13.3 s：63 帧 / 4,695,503 B；17 帧因调色板变化整幅重写（带局部色表）、46 帧差分；合成末帧是完整桌面，无错位或残影。滑屏时整幅变化，体积自然回到 MB 级，这是内容决定的。
  - 平台解码：设备 `screenshot-recording-latest` 对这次真机成品返回 `frames=63:legacy=864x720:animated=true:size=864x720`；`screenshot-recording-format`、`-pipeline` 仍 PASS。
- **工具（本地证据目录）**：`gifinfo.js`（帧数/矩形面积/局部色表/合成画布统计）、`gifcompose.js`（按透明与偏移合成末帧 PNG，供目视核对）、`after.gif` / `scroll.gif` / `motion.gif` / `motion-last.png`。
- **已知差异**：未移植 FFmpeg 的 `shrink_palette`（局部色表固定 256 项，原版会按实际用色收缩到 2 的幂）。只影响调色板频繁变化片段的体积，不影响解码正确性。

## 十五、标注 v3：其余工具、绘图模板与画布裁剪（2026-11-07）

- **上游依据**：`ScreenRecordingController::connectDrawingToolbar`（`screenrecordingcontroller.cpp:585-658`）把**整套**截图调色板接到录制画布上——选择（`connectScreenRecordingSelection`）、形状、箭头、直线、画笔、矩形高亮、笔迹高亮、矩形滤镜、笔迹滤镜、自动筛选、聚光灯、橡皮、水印、文字、序号，外加撤销／重做与 `drawingDeactivationRequested`（清空激活工具 → `InputMode::PassThrough`）。录制侧只把**工具条窗口**排除出采集，画布本身在录制范围内。

- **手机实现**：
  1. 工具条按上游顺序排 12 个工具 ＋ 撤销／重做／清空／退出，共 16 格；屏宽折行（`ScreenRecordingAnnotationLayout.cellsPerRow`，最多 8 格一行，K60 上是两行）。原版是桌面单行，这是手机差异。

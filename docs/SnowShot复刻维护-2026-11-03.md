## 后续修复：编辑挤字与框选直接翻译

用户澄清：框选后「识别」与「翻译」是并列入口；翻译内部先OCR再翻译，不能要求先手动点击识别。

- 工具条有有效选区即显示翻译按钮；无文字时点击由内部发起OCR，成功后自动翻译，已有编辑文字时直接翻译当前草稿。OCR失败可重试，OCR阶段亦可取消；取消后的迟到结果不显示、不触发翻译。
- 编辑入口及点按识别/译文文字均进入统一文档。文档保持16sp，宽度至少240dp/高度至少160dp（受当前可用窗口限制），长内容滚动，不在输入过程中缩小字号或挤回原OCR行高。

## 圆弧消失与长文崩溃

K60 的 `screen-text.enabled=true`，无障碍启用列表也有 `ScreenTextService`，但系统将其列入 `Crashed services`。安装/运行 instrumentation 会重启主进程，长文测试又确认了独立的原生崩溃，都会影响同进程服务；不能只改圆弧样式。重新绑定该组件后，崩溃列表清空并恢复 63×168 的悬浮窗口，其他无障碍服务保持原样。所有测试结束后已再次重绑并确认窗口存在。

600 中文字符的固定测试触发 `SIGABRT`：固定 llama.cpp 的 `llama_context::decode` 断言 `n_tokens_all <= n_batch`；此前 JNI 把整段 prompt 一次交给仅支持 256 token 的 batch。改为按 `llama_n_batch()` 分批预填充，每批检查取消与超时。另修正释放顺序：先解锁 session mutex，再删除 session，避免析构锁后再次解锁。

## 性能取证

同一 100 英文字符，线程顺序为 4/2/3/3/2/4，两轮：4线程 2373–2844ms、3线程 3397–3571ms、2线程 4063–4779ms。第一轮计时含释放，不能与后续严格逐毫秒横比。

第二轮独立参数对照：4线程绑核 Q8 KV 2724/2833ms，不绑核 2952/3109ms，F16 KV 2905/2804ms。未见切换参数的收益，正式默认仍为4线程、绑核、Q8 KV；JNI 参数仅供同路径对照，不新增用户设置。

# Nemotron 3.5 流式 ASR 的 K60 实测（2026-10-20）

本轮真做了下载、桌面对照和 K60 隔离测试，不是资料调研。**结论：暂不替换第一遍流式模型，停止继续堆功能。**
决定性原因不是准确率，而是它在 K60 上跑不进实时：2 线程解码耗时是音频时长的 1.14 倍，改 4 线程没变化，
于是「边说边出字、松手及时上屏」这两条硬要求同时失守。

上一轮只查资料的结论见 [Nemotron-ASR适配评估-2026-10-20.md](Nemotron-ASR适配评估-2026-10-20.md)，
本文用实测数据替换其中「技术上值得做离线候选 A/B」的乐观判断：**A/B 做完了，不通过。**

**运行时接口实测**（这是本轮最重要的可行性发现之一）：

- 1.13.8 的 native 库确实含 `OnlineRecognizerTransducerNeMoImpl`、`online-transducer-nemo-parakeet-unified-model.cc`、

## 2. 对照方法

- **同一批固定音频**，共 **174 条**：既有 60 条（英文整句 8、独立英文词 16、中英混说 16、粤语公开样例 20）
  + 普通话压力集 114 条（短词 12、简单句、长句、否定 8、金额/数字 8、轻声 7、15dB 噪声 7、加速 7、
  600ms 停顿 7、静音 4、冷启动 8）。
- **金标不是模型输出**：中英/普通话由已知文本合成（Microsoft Huihui/Zira），粤语用 sherpa 文档公开
  `yue-*.wav` 及其发布转写；文本先于音频存在。数字 ITN 差异（`三点十五` vs `3点15`）单列，不计错。
- **计分**：中文按字 CER、英文按词 WER、中英混说按「汉字 + 英文词」统一单元错误率；忽略大小写与标点
  （沿用[既有口径](语音中英混合与英文评测-2026-10-17.md)）。正文与标点分开，标点单独统计。
- **桌面**只做准确率筛选，明确不作延迟证据。
- **真机**取 32 条子集，四种模式各跑一遍，全部以 **20ms 真实节奏**投递（代码里有
  `Fixed audio was fed faster than real time` 断言，不是整段灌入）：

| 模式 | 含义 |
|---|---|
| `nemotron-raw-zipformer` | 现有 Zipformer 第一遍原始输出（生产参数：greedy、2 路、`cjkchar+bpe`、2 线程） |
| `nemotron-raw` | Nemotron 第一遍原始输出（`model_type=nemo`、2 线程） |
| `nemotron-raw-t4` | 同上 4 线程，只在「追不上实时」出现明确取舍时补测 |
| `nemotron-pipeline-zipformer` | 现有完整链路（VAD + 二遍 + 改写窗口 + 数字格式） |
| `nemotron-pipeline` | 只反射替换第一遍 recognizer，其余链路一字未改 |

隔离方式：权重推送进应用私有目录、**不打包进 APK**；只重装 androidTest 测试包（`local.voxfix.debug.test`），
主 APK 未重装（`lastUpdateTime` 仍是 2026-10-19 21:04），默认输入法与个人词库、剪贴板、学习记录都没碰。
测试没有新增 `preview/*.test.mjs` 用例（本轮不动前端），验收走 instrumentation。

## 4. K60 真实速度（32 条，20ms 节奏）

| 指标 | Zipformer 第一遍 | Nemotron 第一遍 | Nemotron 4 线程 |
|---|---:|---:|---:|
| 模型加载 | **1,314 ms** | 5,286 ms | 4,492 ms |
| 首字 P50 / P95 | **518 / 2,064 ms** | 752 / 2,003 ms | 880 / 2,280 ms |
| 全程没出字 | 4 条 | 5 条 | — |
| **解码耗时 / 音频时长** | **0.189** | **1.143** | **1.140** |
| 最长句末尾滞后 | 0.05 s | **25.3 s** | 4.1 s |

`1.14 > 1` 的含义很直白：**它算得比说话还慢**。喂得越久积压越多，`long-2-600`（26 秒）末尾滞后 25 秒，
文字一路落后。4 线程没有改善（1.140），说明不是线程数不够，是这颗 CPU 上 0.6B int8 的算力就不够。

完整链路（这才是用户看到的东西）：

| 指标 | 现有链路 | 只换第一遍后 |
|---|---:|---:|
| 松手 → 首次上屏 P50 | **75 ms** | **698 ms** |
| 同上 P95 | 239 ms | 1,748 ms |
| 首个非空文字 P50 | 493 ms | 1,203 ms |
| 二遍在 420ms 窗口内被采用 | 19/32 | 11/32 |
| 二遍迟到（超窗口作废） | 2 | 5 |
| 二遍没回来 | 11 | 16 |
| 最终整句完全匹配 | **26/32** | **24/32** |

松手 698ms 意味着：按住说完松手，要等大约 0.7 秒才看到字，且长句更久（P95 1.75 秒）。
这是**结构性**的，不是调参能救的——它已经把「松手后补渲染尾块」的时间也吃掉了。

**口径更正（同日补测）**：上表「首字」是从音频文件开头算的，而固定音频前面有 200–400ms 静音。
按「真实开口 → 第一个字」重算（同一批音频，阈值 0.02）：

| 场景 | 开口 → 首字 P50 | 最快 | 最慢 |
|---|---:|---:|---:|
| K60 Zipformer 第一遍 | **374 ms** | 294 | 1,435 |
| K60 Nemotron 第一遍（2 线程） | 618 ms | 403 | 1,368 |
| 桌面 9700X Nemotron（2 线程） | 529 ms | 322 | 1,302 |
| 桌面 9700X Nemotron（4 线程） | 522 ms | 313 | 1,291 |
| 桌面 9700X Nemotron（8 线程） | **514 ms** | 338 | 1,300 |

结论：**线程从 2 加到 8 只快 15ms**，说明真正的地板是模型算法（RNN-T + 160ms chunk 需要攒几块才敢出字），
不是算力。桌面比手机快约 100ms 就是算力能贡献的全部。NVIDIA 宣传的「语音结束后 0.07 秒出结果」是
**端点延迟**（说完 → 定稿），不是「开口 → 首字」，两个指标不能混。

## 6. 兼容性逐项

| 能力 | 是否兼容 | 依据 |
|---|---|---|
| 个人词库（拼音/语音学习、同音改字） | 兼容 | 该层在 `emit()` 之后、未改；但二遍采用率下降会让学习触发变少 |
| 热词（术语提升） | **不兼容** | 模型不暴露 `hotwords`/`prompt_dictionary`；1.13.8 的 ContextGraph 热词只走 zipformer transducer。现有「术语进个人语音词典」这条最大杠杆（混说 18.16%→16.49%）在新模型上**完全失效** |
| 语言选择（zh / auto / yue） | **不兼容** | `setOption("language")` 无键可写，只能 auto；实测粤语会串成越南语（`Màu anh thấy sim个又`） |
| 标点 | 名义兼容、无收益 | 首遍只 6/174 自带标点；最终标点仍由 SenseVoice/CT 提供 |
| 数字转换、否定保护 | 后处理未变，但输入变差 | 首遍把 `三点五厘米` 变 `3.  50 米`；最终出现 `请卖两间苹果和三平牛奶`（买→卖、斤/瓶丢失） |
| 松手及时上屏 | **不兼容** | 75ms → 698ms |
| 二遍收尾窗口 | 变差 | 采用 19→11，迟到 2→5 |

## 7. 判定

**暂不值得替换第一遍。** 依据按权重排序：

1. **速度不成立**：`decode/audio = 1.14`，追不上实时；松手上屏 698ms，是现有 75ms 的 9 倍，且 4 线程无改善。
2. **准确率并没有净赚**：桌面 174 条 125→123；真机完整链路 26/32→24/32。混说/英文的收益被普通话简单句、
   否定、金额的退步抵掉，连「混说术语」这种收益最大的场景也出现 `这个punti修好了` 这种反向结果。
3. **代价过大**：+0.56 GB 安装包、+1.0 GB 峰值 PSS、6 倍 CPU 时间、+4 秒冷启动。
4. **现有能力被砍**：热词与语言选择在新路径上都不可用——这两项恰好是 VoxFix 现在最有用的杠杆。

也不建议「再试一版」：算力瓶颈在模型规模（0.6B）与 CPU 后端，换 80ms 分块只会更碎、换 560ms 首字更晚；
真正的出路是 NPU（QNN，缺 `libQnnHtp.so`）或更小的模型，那是另一个课题，不是调参。

**唯一值得保留的线索**：它在「中英混说 + 英文术语 + 长句断句」上的原生表现确实比 Zipformer 好一档
（混说 4/16→9/16、`GitHub/JSON/Python/cache/offline` 全对）。等哪天有能跑实时的后端，再从这三类场景切入。

## 10. 后续盘点：公开的量化/微调版本与真正适合的尺寸（2026-10-20 补）

用户问「社区有没有量化或微调版本、是不是本来就该跑在电脑上」。分开回答，不要混为一谈：

**微调不改速度，只改准确率。** 微调后模型架构、参数量、每 chunk 计算量完全不变；本轮 K60 的瓶颈是
`decode/audio = 1.14`，属于算力不够，微调无法改善。NVIDIA 官方微调教程（五步、NeMo）也明确是可选项调准确率，
`att_context_size` 才是延迟旋钮，而它已经在 160ms 档用过了。

**官方「很快」的语境是 GPU。** Nemotron 3（英文版）宣传的「语音结束后 0.07 秒出结果」以及 3.5 的吞吐数字
（单张 H100 在 80ms 档可跑约 240 路并发）都是数据中心 GPU 上的结论，不能外推到手机 CPU。

**公开可用的 Nemotron 3.5 量化版（同一套权重，换运行时）**：

| 形态 | 体积 | 运行时 | 手机上可直接用吗 |
|---|---:|---|---|
| ONNX int8（本轮测的 sherpa 包） | 682 MB | sherpa-onnx / ONNX Runtime | 能加载，但 1.14× 实时 |
| GGUF `Q8_0` | 716–751 MB | transcribe.cpp / NeMo-Speech.cpp / CrispASR（ggml） | 无 Android 绑定，未验 |
| GGUF `Q6_K` | 593–621 MB | 同上 | 未验 |
| GGUF `Q5_K_M` | 534–560 MB | 同上 | 未验 |
| GGUF `Q4_K_M` | 473–496 MB | 同上；作者称桌面 CPU 约比 F16 快 2× | 未验 |
| GGUF `F16/F32` | 1.19–2.55 GB | 同上 | 不适合 |

**公开的中文微调版确实有**：`Luigi/nemotron-3.5-asr-streaming-0.6b-zhtw`（v3，台湾国语，Common Voice zh-TW
CER 9.81，输出简体），作者同时放了 Android **LiteRT INT4** 包（约 663 MB，需 LiteRT-Next / NNAPI）。
它的 zh-CN 槽位 CER 13.2%（INT4）/11.57%（fp32），是**台湾国语语料**上的数字，与 VoxFix 自建语料不可比；
且要换 LiteRT 运行时，不是 sherpa 现成路径。**没有**大陆普通话的公开微调版。

**真正适合手机键盘的尺寸还是小流式 Zipformer**（现在 117 MB、0.19× 实时）。若还要找升级，只有一条值得摸：
`X-ASR zh-en 2026-06-05`（Apache-2.0，自带标点，160/480/960/1920ms 四档，sherpa 有现成包）。
其 FP32 打包 615 MB，按 int8 约 1/4 推算 encoder 约 140–160 MB，与现有 105 MB 同量级——**未实测，不作结论**。

**电脑端才是这类模型的主场**：Windows 上有现成的 ggml 运行时（transcribe.cpp / NeMo-Speech.cpp / CrispASR），
Q4_K_M 只要 473 MB，9700X 的 AVX2 与 5060 Ti 都够用。若要替代电脑上的听写，值得单开项目，与 VoxFix 完全解耦。

# 个人语音词典与纠正学习：可行性（2026-10-18）

后续执行状态：已按本计划完成首版并保留数据安装，具体源码、K60隔离成长闭环、数据保留及未验边界见[实现记录](../个人语音词典与纠正学习-实现-2026-10-18.md)。以下保留调研与计划形成时的说明。

本轮是调研与方案，未改运行代码、构建或安装。用户希望手动添加常用词，语音识别优先使用个人用词，并从听写后的改字中逐步学习；拼音已有个人词库，优先发展语音。

## 结论

建议采用「共享个人词条 + 分开的拼音/语音权重 + 语音纠正记录」。先实现手动语音词典与流式热词，接着实现保守的改字学习。不需要先训练新模型，不恢复安卓 Qwen。不能保证添加一个词以后任何上下文都绝不误识别。

## 外部证据

- Typeless 官方明确支持手动添加词或短语、CSV 导入，以及听写后纠正单词自动加入 Auto-added。这证明产品行为，不证明它逐人训练了声学模型，也未公开其具体纠错算法。[官方词典说明](https://www.typeless.com/help/quickstart/history-and-dictionary)
- Typeless 还单独描述语气、详略等写作风格个性化，不能与识别词典混为一谈。本项目当前诉求主要是忠实识别与术语偏好。[官方个性化说明](https://www.typeless.com/help/quickstart/personalization)
- OpenWhispr 是有实际纠正学习证据的开源参考，MIT 许可；其已合并 PR 说明通过 Windows 编辑框读取用户修改来更新字典。可借鉴差异捕获、词典和误学撤销的设计，不能照搬 Windows UIA 到 Android。[PR #665](https://github.com/OpenWhispr/openwhispr/pull/665)、[变更记录](https://github.com/OpenWhispr/openwhispr/blob/main/CHANGELOG.md)、[许可](https://github.com/OpenWhispr/openwhispr/blob/main/LICENSE)
- sherpa-onnx 官方热词用于 transducer，要求 modified_beam_search；属于推理加权，无需重新训练。SenseVoice 不属于该通路。[官方热词文档](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)
- 项目固定版本 1.13.8 的 Kotlin API 已有 createStream(hotwords)，也有解码、模型分词单元及 BPE 词表配置。英语/中英混合热词需匹配当前模型的分词资源，不能把中文拼音当作热词 token。[固定版本 API](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/kotlin-api/OnlineRecognizer.kt)
- 上游另有 HomophoneReplacer，可用于 Zipformer 和 SenseVoice 的汉字拼音规则替换；只处理汉字、规则提前生成且不支持动态修改，官方生成步骤使用 pynini。因此适合少量固定术语试验，不是拿来即可不断成长的移动词典。[官方说明](https://k2-fsa.github.io/sherpa/onnx/homophone-replacer/index.html)、[1.13.8 SenseVoice 示例](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/java-api-examples/NonStreamingDecodeFileSenseVoiceWithHr.java)
- SenseVoice 上游有音频与标注文本的微调流程，但这与向现成 ONNX 推理器添加词条是不同工作。个别改字不能证明需要微调；后续真要适配口音，需另行授权收集音频、划分训练/验证集、训练、导出量化并重验 K60。[上游微调说明](https://github.com/QwenAudio/SenseVoice#finetune)

## 当前代码事实

以本轮工作区为准，存在其他未提交语音/前端改动；没有修改或覆盖它们。

- `PersonalLexicon.kt`：SQLite personal-lexicon.db，记录输入键、词、读音、hits、导入标记；已有版本1备份、合并导入与迁移。当前 schema 不能直接表达语音纠正关系、语音权重和英语混合词；不是把所有语音词硬塞入现有拼音键即可完成。
- `preview/app.mjs` 的 recordChoice：真实拼音选词才记录，排除密码、禁止学习字段、搜索和引用编辑；这套隐私约定应覆盖新增原生语音学习。
- `SpeechEngine.kt`：Zipformer transducer 第一遍，未显式指定解码方法，上游1.13.8默认 greedy_search；createStream() 未传个人热词。SenseVoice 第二遍已有结果保护和语种采用逻辑，但尚未读个人词库。标点/数字转换另有既有输出链路。
- `SpeechSegment.kt`：第二遍完成才通过 refine 采用，否则保留第一遍。新增词典必须覆盖采用阶段，否则第一遍正确人名可能被第二遍改回。
- `VoxFixImeService.kt`：语音提交后清空当前语音文本，尚未看到维护「原识别片段—用户修改」关联的实现。已有 InputSession、输入框代次、选区与 InputConnection 路径可以复用，不需辅助功能全局监听。
- `docs/长期个人词库与迁移-2026-10-17.md` 已明确默认学习、数据保留、备份与密码/禁止学习边界；应延续，而不是恢复旧 Rime 学习库。

## 词库如何共享

| 内容 | 共享方式 |
| --- | --- |
| 人名、地点、术语的正确写法 | 共享，一处管理和备份 |
| 完整读音 | 能确认才共享，多音字允许用户校正；普通话拼音不可直接当粤语读音 |
| 拼音选词次数 | 保持拼音自己的统计，不等同语音权重 |
| 语音优先词、手动指定 | 单独来源与权重，手动添加立即进入语音候选词集合 |
| 误识别→改正 | 语音独有，保存局部词/必要上下文、确认次数、最近使用及撤销信息 |
| 英文/混合词 | 共用管理入口，但无需伪造中文拼音，语音按模型分词处理 |

可以沿用同一个数据库与词库页面，按需要增表/升级备份；必须兼容旧版数据并验证失败回滚。拼音学习的可靠词可提供弱语音先验，明确语音修正的词若能确认读音也可供拼音召回，但两者不互相机械累加频率。

## 分步落地

### 第一步：手动词典 + 热词验证

复用词库入口，添加正确词语，中文提供可校正读音；不要求录一遍。先选少量个人术语作热词，不把整个词库无上限强推给解码器。配置 modified_beam_search 及正确分词资源，验证当前移动模型、未知 token 和动态会话词更新行为。

词库全部长期保留；识别时只取有限的有效词集合，最近使用、手动指定、已确认纠正优先。词频要有上限/平滑，不能直接把数千次拼音 hits 当热词分数。热词是提高机会，不能覆盖音频证据。

先对固定音频比较无词典/有词典及速度。个人热词可能改善特定词，但 beam 解码会增加计算，不能预先宣称手机开销可忽略。两遍取舍应保护已被音频与词典共同支持的专名，不能仅凭第二遍不含词库词就整段拒绝它；标点和数字链路继续沿用原顺序。

### 第二步：纠正后学习

1. 只在内存保留本次已成功提交的语音片段、输入框身份/代次和有限锚点，建立短期可追踪范围。
2. 对同框紧接发生的局部编辑做差异比对，等拼音 composing 完成后再确认修改。正文可通过 InputConnection 读取，但宿主可能返回 null 或无法提供稳定范围；不能假定所有应用都能捕获。[Android 接口](https://developer.android.com/reference/android/view/inputmethod/InputConnection)
3. 例如「联系张月」改成「联系张玥」，形成目标词证据；「明天去」改成「后天去」是改意图，默认不学永久替换。纯标点、格式化、粘贴整段或宿主自动改写不作为可靠纠正。
4. 自动一次改字先作弱证据，重复独立纠正后增强；手动指定词可以立即生效。没有修改不等于确认正确，原始识别不自动喂回作训练目标。
5. 换框、换应用、锚点丢失、超时或敏感字段，停止追踪；无法确认则跳过。持久化局部词与纠正证据，不保存整句正文或日常录音；支持纠正误学和针对单词撤销，不增加日常调试面板。

只靠同音关系也有歧义：「会议」和「回忆」都合法，不能建立全局无条件替换。更不能把同义词偏好当语音错词，强行将「购买」改为「买」；那属于另一个润色需求。中文拼音只用于候选召回，实际替换仍需上下文与确认强度。

### 第三步：仅在必要时评估模型微调

若固定词典与纠正记忆解决不了持续的口音/声学误差，再独立评估微调。文字词典可在不保留录音的前提下成长；声学微调需要音频与正确文本，不能在当前不存日常录音的约定下暗中开展。训练后的输出是否能继续固定版本 sherpa-onnx 推理、量化后质量如何，均需另验。

## 2026-10-18 方案收敛：共享习惯，按证据使用

用户进一步要求最小修改、优先成熟技术，并质疑「语音与拼音分别计算偏好」是否意味着口语和书面语分离。

明确推荐：**一份个人词典、共享用词偏好、保留不同来源的学习证据。** 不建立两套相互独立的用户画像，不主动把口语改成书面语。先前「分别计算偏好」指两类输入不能直接复用同一个分数，不是把用户的语言习惯割裂。

- 手动指定「张玥」：明确偏好，语音立即优先；能确认读音才加入拼音召回，不猜多音字。
- 拼音反复选择「张玥」：提供共同用词先验，语音可以受益，但不把拼音 hits 原样设成热词分数。
- 语音从「张月」改成「张玥」：增强共同目标词的证据，并保留语音独有的误识别关系；不要拿错误词去改变拼音的输入键匹配。
- 原始语音反复输出「张月」而用户未修改：不当作确认，避免错误自我强化。

理由是观测可靠性与解码方式不同：拼音有用户输入键，语音有音频候选；明确选词、主动改字、未修改结果的证据强度也不同。口语/书面语只是可能存在的上下文因素，不是本方案拆分权重的依据。

### 用户已确认的学习策略

**自动纠正渐进增强，手动加词立即优先。** 自动纠正第一次即可提供有限偏好，重复独立纠正继续增强；不设「一定累计两次才开始有任何效果」的硬门槛，也不把任何次数解释为必定替换。具体分值用正反例校准，不凭空固定。

### 本次补查的技术选择依据

- sherpa热词是现成推理能力；1.13.8 Kotlin已暴露动态会话热词入口，优先复用，不自写波束搜索或另一套识别器。[固定版本API](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/kotlin-api/OnlineRecognizer.kt)
- OpenWhispr官方记录显示纠正监控已于1.5.4发布，后续修过CJK及宿主兼容问题。可复用设计经验，不能据此断言中文学习准确率或安卓适配已成熟；不移植整套桌面框架。[官方变更记录](https://github.com/OpenWhispr/openwhispr/blob/main/CHANGELOG.md)
- Typeless官方的手动/自动词典，以及Wispr Flow官方的词表和「误拼→正确词」两列导入，都支持将词条和纠正关系分开表达的方向；它们的内部算法并未因此公开。[Typeless](https://www.typeless.com/help/quickstart/history-and-dictionary)、[Wispr Flow](https://docs.wisprflow.ai/articles/8955301725-How-Do-I-Bulk-Import-Dictionary-Items-and-Snippets)
- HomophoneReplacer官方说明规则需预生成、不支持动态修改，适合固定术语原型，不作为自动成长核心；暂不引入pynini/FST移动生成链。[官方文档](https://k2-fsa.github.io/sherpa/onnx/homophone-replacer/index.html)

暂缓声学微调、风格润色、云同步、应用分类画像和整体拆文件。没有证据支持在这些技术中宣称某一种中文准确率「全网最好」；当前选择依据是既有接口可复用、已有公开实现，以及与本项目离线/低延迟/数据保留要求匹配。

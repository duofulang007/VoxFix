## 总体判断

当前由成熟开源识别内核、Android采音接口和项目自定义的分段、二遍采用、个人纠错策略组成。架构适合全离线实时输入，不需要整体重写；但模型选型与端到端质量验证不足，不能称为已经确认的最佳组合。最优先的问题是二遍粤语微调权重的用途匹配，其次是流式基座对照，以及最后一句能否真正得到二遍修正。

当前路径：16kHz单声道PCM16采音 → 20ms有界队列 → 2023双语Zipformer实时文字；Silero按停顿取音频 → SenseVoice后台二遍 → 文本规则选择结果 → CT-Transformer标点/数字转换/个人纠错 → InputConnection提交。各阶段并非全程串行：采音与识别解耦，二遍后台执行，松手不等待未完成二遍。

本地四个代表文件实算SHA-256与准备脚本一致：流式encoder `f559f4…`、SenseVoice `12ca1a…`、VAD `9e2449…`、标点 `65a3fb…`。这是本机源权重确认，未重新核对手机APK。

## 各环节成熟度与处理建议

| 环节 | 当前事实 | 判断及优先级 |
|---|---|---|
| 采音与队列 | Android AudioRecord、VOICE_RECOGNITION、16kHz PCM16、20ms块；PcmCapture约3秒有界队列，积压显式失败 | 平台接口与实现思路成熟，保留。真实麦克风首尾、轻声及噪声仍需真人验证；无证据支持直接加降噪或换采音框架。 |
| 流式基座 | 2023-02-20 mobile中英双语Zipformer；有个人词时2路modified_beam_search，否则greedy | 主要模型升级候选。官方有2025-06-30中文流式普通版约160MB及加大版，但中文标注不能代替混说验收。先做对照，不能凭日期判胜。 |
| 分段与补尾 | Silero报停顿后再累计0.25秒；段提交补两块200ms静音再reset；最终inputFinished | 已修复旧基座的真实丢尾块问题，但时序与旧模型320ms块强相关。换基座后重测块长、边界与上下文，不能机械沿用最优参数。 |
| 二遍 | 2025-09-09 SenseVoice粤语微调，auto；后台单队列 | 开源模型本身成熟，当前用途需优先复核。普通话原版2024是必要对照，不应直接先加近1GB新模型。 |
| 二遍采用与收尾 | 0.85文本相似度、英文/数字/否定保护和语种正文判断；松手不新启二遍，SpeechSegment.finish不等未完成任务 | 项目自定义启发式，不能当作校准过的置信融合。保守规则会挡错改，也可能挡正确结果；短句和最后一句未必受益于二遍。要统计二遍完成率、采用率、正确但被拒绝次数。 |
| 标点 | 2024-04-12 CT-Transformer INT8，含汉字才使用；纯英文只用句末规则 | 官方仍提供的中英模型，可暂留。当前英文自然标点功能不足；源码150ms只限制等待加载，实际addPunctuation同步推理不在该超时内，不能承诺总收尾≤150ms。 |
| 数字格式 | 项目规则转换时间/金额/单位，保护模糊数量 | 这是规则代码，不存在模型版本可升级。保留金额、否定和歧义保护，换二遍后测ITN与二次格式化兼容。 |
| 个人学习 | 官方热词解码+项目同音/上下文纠错；不更新声学模型权重 | 热词机制成熟，自动纠正策略为近期开发；隔离平台与合成音频通过不等于长期误学习率已验。保留已有数据；换词表时复核热词编码覆盖与误替换。 |
| 运行与构建 | sherpa-onnx1.13.8；构建机ORT1.31.0预优化图；语音按需加载、空闲释放 | sherpa已是当前最新release。构建机ORT与Android随库运行时是不同角色，不因数字不同就另行替换手机运行库。现有预优化脚本和Gradle词表校验写死旧模型，换权重要同步修改。 |

## SenseVoice：当前权重与普通话主用途不匹配

**可以确认**：`tools/setup_voice.py`固定下载`2025-09-09`；随包的`android/app/src/main/licenses/sensevoice/UPSTREAM.md`也明确指向ASLP-lab的`WSYue-ASR/sensevoice_small_yue`，不是仅凭日期猜测。

[sherpa官方预训练页](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)明确说明：2025-09-09在2024-07-17基础上用21,800小时粤语微调，且不支持标点；2024-07-17来自iic/SenseVoiceSmall，开启ITN支持标点。两者都列出五种语言，但“仍支持普通话”不等于普通话效果更好。

[Handy讨论#1274](https://github.com/cjpais/Handy/discussions/1274)中，sherpa维护者csukuangfj于2026-04-12明确表示新版专用于粤语，不聚焦粤语时不要切换，普通话使用旧模型。讨论发起者关于新版全面改善混说、噪声等说法是用户建议，**不能当作维护者或官方测评结论**。

**判断**：对于VoxFix以普通话和中英混合为主的用途，当前二遍选型偏离上游建议，应列为高优先级复核项；不能把2025版描述为通用升级。最小有依据的对照是保持其余链路不变，比较2024-07-17与现有2025-09-09。上述资料足以确认用途错配风险，尚不能证明它导致了本项目多少识别错误，也不能承诺回退提高多少。

本项目已经用独立CT-Transformer补标点，因此“2025版不产标点”是已知限制，有现有补偿。不能直接推断换回2024后就应删除独立标点：必须检查两遍采用策略、尾段、数字转换顺序以及是否重复补标点。

## sherpa-onnx：项目版本已经是当前最新release

本次打开[官方latest](https://github.com/k2-fsa/sherpa-onnx/releases/latest)跳转到[v1.13.8](https://github.com/k2-fsa/sherpa-onnx/releases/tag/v1.13.8)，标记为Latest。项目`android/app/build.gradle.kts`依赖同版本AAR，随包`licenses/sherpa/UPSTREAM.md`记录官方来源及SHA-256。

因此不能将问题概括为“底层推理库陈旧”。最新运行库不代表所选声学权重最新或适合；本轮仅核对声明及上游发布状态，未重新校验AAR二进制或手机安装包。

## Silero VAD：确认身份线索，版本尚不能下定论

[Silero官方最新release](https://github.com/snakers4/silero-vad/releases/latest)当前是[v6.2.3](https://github.com/snakers4/silero-vad/releases/tag/v6.2.3)。这一release主要调整Python音频依赖，不能仅据版本号推断安卓VAD识别改善。

项目取的是sherpa `asr-models/silero_vad.onnx`，没有上游Silero版本号。脚本固定SHA-256为`9e2449e1087496d8d4caba907f23e0bd3f78d91fa552479bb9c23ac09cbb1fd6`；本地明确路径`models/vad/silero_vad.onnx`为643,854字节，本轮实算hash与之相同。

[sherpa VAD文档](https://k2-fsa.github.io/sherpa/onnx/vad/silero-vad.html)将同一下载路径列为k2-fsa自行导出的16kHz专用629 KB模型，同时另列原始v4、v5模型；文档还介绍了v4逆向导出路径。这支持“项目使用k2-fsa维护的小型16kHz导出”的身份判断，但没有提供当前项目hash与Silero tag的严格映射，本轮也未重新拉取远端二进制比对。

**结论**：不能说项目已用Silero最新权重，也不能只按文件名认定是v6，或草率把它归为错误选型。升级前须核对模型输入/状态接口、sherpa兼容性与K60切段行为；VAD主要影响漏检、误切段和延迟，不会自动修复词汇识别错误。

## 下一步最小验证

1. 先以当前最新版重新建立基线，分普通中文、轻声/噪声、自然混说、英文术语，分别记模型原始结果和最终提交；不能沿用旧40条合成集22/40当作当前日常准确率。
2. 保持其余链路不变，比较SenseVoice2024/2025的中文、混说、标点、数字和语种标签；这是低改动的用途修正验证。
3. 独立比较当前双语流式与2025中文流式；再将胜出的第一、二遍组合跑整条链，确认热词、分段、尾段及输出采用没有把收益丢掉。
4. 同时报告首字/更新间隔/松手到最终提交、二遍完成与采用率、内存。真人麦克风和跨App由用户实际操作验收。
5. 如果上述组合仍不足，再以Qwen3-ASR0.6B或Fun-ASR-Nano作精度对照，达到精度与延迟要求后才决定替换二遍。详见[候选调研](语音准确率方案调研-2026-10-18.md)。

sherpa1.13.8暂不升级；VAD先补清版本来源，不与识别模型同时变更。标点模型暂留，单独修正总延迟预算的实现/表述，并验证英文标点需求。两遍融合的规则应随模型对照调整，避免模型换了、旧门槛仍拦住正确输出。

未重跑识别或进行K60操作；上述为上游资料与本地配置/单文件hash事实，不是新模型真机验收。

# 安卓离线翻译候选核查

核查时间：2026-11-03。用户的约束为**离线、多语言译成中文、准确率优先，同时控制安装包、总存储及内存**。这里只核官方文档、模型卡、文件指针与源码；没有下载任何翻译权重、向手机安装语言包或执行模型推理，没有修改生产依赖或语音运行库。

## 当前结论

不能把 ML Kit 的约30MB语言包称为“识别/翻译准确率最好”。它是小占用、成熟安卓接口的基线。若用户接受约462MB的独立模型文件，**Hy-MT2-1.8B的1.25bit/STQ1_0应成为多语言质量候选的首轮实测对象**；这是候选优先级，不是已测出的冠军。ML Kit、Hy-MT没有在本项目同一真实屏幕文本集上比较过，不能由供应商各自的宣传表推导胜负。

2026-05-21发布的 Hy-MT2 已有官方1.25bit、2bit GGUF文件，不应继续仅把1.5当作最新方案。MT2支持33种语言，官方声明其量化版用于端侧，语言列表包含英、日、韩、法、德、俄、阿拉伯语等。[官方MT2模型卡](https://huggingface.co/tencent/Hy-MT2-1.8B)、[正式1.25bit模型卡及文件入口](https://huggingface.co/tencent/Hy-MT2-1.8B-1.25Bit-GGUF)。

## K60的关键：STQ1_0不是SME2专属

Hy-MT1.5 1.25bit官方示例包含骁龙888/8GB、骁龙865/8GB和骁龙7+Gen2设备，说明该路线并非只针对最新SME2手机；这些是上游演示，不是K60速度数据。[官方1.25bit卡的演示与部署说明](https://huggingface.co/tencent/Hy-MT1.5-1.8B-1.25bit)。

直接核查 `llama.cpp` 的STQ补丁：PR [#22836](https://github.com/ggml-org/llama.cpp/pull/22836) 在本次查询仍是 **open、merged=false**，head固定为 `1e411d8f5a1e23525fa3265dfb4bd76265465397`。不能拿任意stock llama.cpp发行版就假设支持该GGUF类型。官方MT2量化卡也专门提示依赖该STQ内核。

该head的 [ggml/src/ggml-cpu/arch/arm/quants.c:1685–1789](https://github.com/sjl623/llama.cpp/blob/1e411d8f5a1e23525fa3265dfb4bd76265465397/ggml/src/ggml-cpu/arch/arm/quants.c#L1685) 实现了 `ggml_vec_dot_stq1_0_q8_K`：1704有ARM dotprod分支，1710有不具dotprod的ARMv8 NEON路径，1788有通用fallback。源码不存在“必须SME2才可运行”的前提；能编译仍不等于K60上足够快，必须核对实际CPU分支、模型类型兼容和输出。

2bit MT1.5的官方卡强调SME2优化并比较Neon路径，因此K60不能照搬Apple M4/vivo x300的加速数字，也不能反过来说2bit完全无法运行。[官方2bit部署说明](https://huggingface.co/tencent/Hy-MT1.5-1.8B-2bit)。

官方MT1.5演示APK在文件列表中约7.38MB，GGUF则另列约462MB，这支持“程序与模型分开交付”的路线，但不是VoxFix新增安装包大小的实测值。[官方演示文件列表](https://huggingface.co/AngelSlim/Hy-MT1.5-1.8B-1.25bit-GGUF/tree/main)。

## 和现有语音运行库的关系

本项目当前 `android/app/build.gradle.kts:66–69` 包含静态链接sherpa的语音AAR及独立 `onnxruntime-android-1.17.3.aar`；`DesktopCtcDecoder.kt` 使用该ORT。**不为翻译候选贸然更换它**。

Hy-MT STQ GGUF是llama/ggml路线，不能直接交给现有ORT Java接口加载。最小可测方案是独立测试包中的ARM64 llama JNI，固定上述内核来源，先验证模型加载、tokenizer/chat template、EOS及取消释放，再考虑与现有语音共存。初次先CPU路径，不依据官方网页直接承诺GPU/NPU加速。

OPUS ONNX有复用现有ORT的可能，但不能由“.onnx”后缀认定兼容：ORT1.17支持ONNX opset最高20、IR最高9，候选图的实际opset、量化算子、合并decoder分支和KV缓存输入须逐一验证。[ORT官方兼容表](https://onnxruntime.ai/docs/reference/compatibility.html)。

OPUS原模型是Marian encoder-decoder，使用规范化及SentencePiece；中文目标还涉及目标语言前缀，不能仅做字符切分。Xenova目录同时提供source/target spm、vocab及tokenizer JSON；选一种完整一致的分词链，避免重复打包。量化和merged图需要逐token生成及past缓存处理，并非一次 `session.run()` 就得到中文。[原模型卡及预处理](https://huggingface.co/Helsinki-NLP/opus-mt-en-zh)、[ONNX文件列表](https://huggingface.co/Xenova/opus-mt-en-zh/tree/main/onnx)、[分词文件列表](https://huggingface.co/Xenova/opus-mt-en-zh/tree/main)。本轮HF直连API部分超时，OPUS仅记录页面显示的近似大小，没有谎称拿到完整精确清单或跑过本机。

## 下一步应测什么

以下是建议的评测路线，**不是已获得用户模型下载授权、不是已完成实现**：

1. 固定一批同样的OCR原文，先将翻译质量与OCR错误分开。覆盖英、日、韩、德、俄、阿拉伯语到中文，增加数字/金额/否定/专名/混排与多段上下文；不得只挑英文短句证明多语。
2. Hy-MT2 1.25bit对比ML Kit小包基线；确有明显量化失真时再加入2bit对照，不一次把多个大模型装到用户日常主包。
3. 看漏译、数字错误、专名、语义与术语一致性；官方公开基准只作参考。用同文、同上下文、同生成策略比较，OCR识别率和翻译质量分开报告。
4. K60分别测冷启动、热推理、短句/长段P50和P95、峰值PSS、回收后占用、取消/锁屏/旋转；还要观察与当前语音预热共存时的峰值。翻译惰性加载、退出释放是应验证的实现目标，不提前承诺“只占440MB RAM”。
5. 翻译作为可替换结果提供者接入现有内存截图会话，版式继续由文字框坐标管理。用户确认采用哪一包、何种下载/导入方式后，才部署模型到手机。

本轮没有任何候选的K60翻译质量、延迟或内存实测，不能称“当前最优解已验证”。源码与元数据证据在忽略目录 `.android/snow-shot-eval-20261103/translation-metadata/`；主程序仍以实际依赖/安装状态为准。

## 用户后续范围澄清

2026-11-03：只需要英语、日语、韩语转中文；中文原文直接识别和编辑。方向限制不能直接裁掉HY多语密集权重。待统一测试三种方向后比较MT2 2bit约600.53MB、1.25bit约461.86MB以及Q4_K_M约1.13GB；目前不声称任何一个在K60上质量最好、延迟或内存已达标。

主包翻译模型尚未选择或替换，未向手机下载语言包。本轮已准备Snow原版图标资源/许可及原位文字层源码，仍未接入截图操作条或安装为完成版；不能把源码编译检查视为OCR/翻译/原位编辑整条链路已通过。

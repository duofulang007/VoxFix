# 剪贴板图片编辑修复（2026-11-13）

> 用户反馈三件事：①剪贴板里的图片点编辑后「画面错误、完全不是正常画面」；②长截屏/普通截图都没有
> 「改过的内容能再次点进去继续改」；③插线自动投屏到电脑的后台程序不见了。
> 本文记录根因与改动，验证状态按「构建 / 安装 / 真机」分开写。

## 1. 根因

| 现象 | 根因 | 代码位置 |
| --- | --- | --- |
| 图片在编辑器里变形、画面混乱 | 画布是 `ImageView` + `ScaleType.FIT_XY`，把任意比例的图**非等比拉满全屏**。长截图 916×10192 塞进 1080×2400 会被纵向压到约 1/4；框选出来的非全屏截图同理被拉伸 | `ScreenshotCaptureOverlay.kt`：`background`、`content` 的 `-1,-1` 布局 |
| 剪贴板预览页整页错乱 | 预览用 `<svg viewBox="0 0 W H">` + CSS `height:auto;flex:1`。长图的 `height:auto` 会算出几十倍宽度的高度，容器被撑爆，整块面板布局崩掉；普通截图也会被同一个规则波及 | `preview/style.css`、`preview/app.mjs` 的 `imageClipboard()` |
| 长截图没有可二次修改的内容 | 长截图入库走 `ScreenshotStore.savePng`，只写普通图片记录（`Kind.IMAGE`），**不带 `ScreenshotDocument`**；编辑器打开时只能用 `ScreenshotDocument.full()` 造一个空工程，之前的内容无从恢复 | `ScreenshotStore.savePng`、`ScreenshotScrollCapture` 保存分支 |
| 插线不投屏 | 单实例保护只看「PID 是否存活」。Windows 复用 PID：记录里的 9496 被 `DefenderAiPlatformHost` 占用，companion 每次启动都误判「已有实例」后自杀（日志 2026-11-13 13:51:03） | `tools/voxfix_phone_companion.py`：`single_instance()` |

## 2. 改动

### 2.1 画布等比（Android）

- `ScreenshotCaptureOverlay` 增加 `fitCanvas(w,h)`：`scale = min(w/image.width, h/image.height, 1f)`，
  `content` 的布局尺寸取 `image 尺寸 × scale` 并居中。
- 之所以只改布局尺寸就够了：选框（`ScreenTextRegionView`）、绘图层（`ScreenshotDrawingLayer` 的
  `canvas.scale(width/image.width, height/image.height)`）、文字层（`ScreenshotTextLayer.render`）
  全部是「image 尺寸 → 视图尺寸」的线性映射；视图尺寸按同一比例算出，映射即恒为等比。
- `root` 加纯黑底，画布缩小后四周不再透出宿主应用。
- 普通截图（1080×2400）算出的 `scale` 正好是 1，布局与改动前一致；非全屏框选截图此前会被拉伸，
  现在等比居中并留黑边。
- `scale < 0.9` 时提示一次「长图已按比例缩小显示，需要精细编辑可先裁剪」，避免用户误以为画面出错。

### 2.2 长截图工程化（Android）

- `ScreenshotStore.savePng(..., document: ScreenshotDocument? = null)`：传 `document` 时按工程结构落盘
  （`projects/<id>/source.png` + `1/composite.png` + `1/thumbnail.webp` + `1/document.json`），
  entry 记为 `Kind.PROJECT`、`revision=1`；不传则保持旧的普通图片路径。
- `ScreenshotScrollCapture` 两个保存分支都带 document：
  - 单段：`saveProject(ScreenshotDocument.full(w,h), output, source = output)`；
  - 多段：`savePng(..., document = ScreenshotDocument.full(crop.width(), total.toInt()))`。
- 效果：长截图与普通截图一样可以反复点「编辑」，保存时 revision 递增，上次加的对象、文字仍在。

### 2.3 剪贴板长图预览（前端）

- `imageClipboard()`：高宽比 > 2.2 的图片改用 `<div class="clip-image-scroll"><img></div>`，
  按宽度铺满、纵向滚动；普通截图与裁剪模式仍用 SVG。
- `.clip-image-canvas` 的 `height:auto` 改为 `height:100%`，SVG 在 flex 容器内不再可能把面板撑爆。

### 2.4 伴生工具（投屏）

- 单实例判定改为 `msvcrt.locking` 独占锁（`companion.lock`），锁随进程退出自动释放，不受 PID 复用影响；
  `companion.pid` 仍然写入且可读，便于观测。
- 计划任务 `VoxFixPhoneHelper` 增加「每天 21:20 起每 5 分钟重复」触发器（`MultipleInstances=IgnoreNew`），
  进程静默死亡后最迟 5 分钟内被拉起；原有「登录启动 + 失败重启 5 次」保留。任务 XML 备份在
  `.android/voxfix-companion/VoxFixPhoneHelper.backup.xml`。

## 4. 已知限制


- 手机端没有可滚动的画布：**长截图在编辑器里等比缩进一屏**（本次数据 916×10192 → 约 216×2400），
  比例正确但精度有限；需要精细编辑时先用「裁剪」取一段另存，再编辑那一段。
- 编辑普通图片（`Kind.IMAGE`）后保存的是**新记录**，原图保留不动，列表里会出现两条；这是既有设计，
  本次未改动。
- 计划任务自愈周期 5 分钟，插线后投屏最多延迟 5 分钟（正常情况仍由 `track-devices` 事件毫秒级触发）。

## 5. 编辑元素可继续修改（用户核心需求）

- `ScreenshotStore.saveProject` 放开 `Kind.IMAGE`：`replaceId` 指向普通图片时**原地升级**为工程，

  迁移顺序为「先 copy 到工程目录 → 索引最后提交 → 成功后删旧 `<id>.png`/`.webp`」，任一步失败只删工程目录，原图不动。

- `ScreenshotDocument` 增加 `activeTool: String?`、`activeStyle: ScreenshotDrawingStyle?`：
  `currentDocument()` 写入、`restoreProject()` 恢复（工具 + 颜色/线宽/字号），旧工程缺键按 SELECT + 默认样式打开。
  `ScreenshotDocumentCodec` 抽出 `styleJson()` 与对象样式共用同一份键。

## 6. 预览与编辑同一形式

- `ScreenshotCanvasFit.kt` + `preview/image-fit.mjs` 共用同一公式：`containScale = min(1, vw/iw, vh/ih)`、
  `widthScale = min(1, vw/iw)`、`canFitWidth = widthScale > containScale*1.05`；两侧单测跑同一矩阵。
- 原生 `ScreenshotCaptureOverlay`：`fitCanvas` → `applyCanvasFit`（CONTAIN/WIDTH），右上角独立「适应宽度 / 整幅显示」
  切换条（不进 `ScreenshotAction`）；`applyCanvasOffset()` 是唯一写 `content.translationY` 的地方。
- **单位冻结**：首次按整幅宽度写 `savedPixelUnit/savedFontUnit`，切模式不会把已存笔画算细、字号算小。
- **坐标统一**：`canvasLeft/Top/ScaleX/ScaleY/canvasX/canvasY` 替换 `placeControls`、分组弹层里的
  `root.width/height` 换算（修本次等比画布引入的锚点偏移）；`setEditingViewport` 改 content 坐标口径。
- **平移手势**：`content.onInterceptTouchEvent` 仅在「WIDTH + 画布高于屏幕 + 无绘制工具或 SELECT +
  非编辑/无弹层/无区域操作/非移动模式」下，垂直位移超过 slop 且明显大于水平才拦截；边界夹取、无惯性。
- 前端预览：`imageFit()` 判定，`contain` 用 SVG、`width` 用 `.clip-image-scroll > img`；切换按钮绝对定位于
  图片右上角，不占动作行（那一行必须四个按钮一行放下）；重新打开记录回到整幅。

## 11. 交互改版：按钮切换 → 照片查看器式缩放拖动（22:40）

用户口径：不要「适应宽度 / 整幅显示」切来切去，改成手指自定义——双指外扩放大、内缩缩小，
到达比例后停住，拖动像看照片/编辑照片一样。

### 交互模型
| 手势 | 行为 |
| --- | --- |
| 双指捏合 | 以双指中心为锚点连续缩放，范围 `1×`（整幅）～`maxZoom`（≈ max(4, 满宽倍数×1.2)，上限 12×） |
| 双指整体移动 | 同时平移（与缩放并用） |
| 单指拖动 | 二维平移，仅在 `zoom>1.02` 或画布高于视口、且没有选中绘制工具时生效（`SELECT` 允许，点按仍选中对象） |
| 双击 | 整幅 ↔ 满宽，220ms 动画、以双击点为锚点；两者相同时（普通截图）不响应 |
| 松手吸附 | `zoom` 落在 `1±0.06` 或 `满宽±0.08` 内自动动画到档位 |
| 边界 | 内容小于视口居中；超出时边缘不越界；无回弹、无惯性 |

### 实现要点
- `content` 布局尺寸固定为整幅尺寸，缩放走 `scaleX/scaleY` + `translationX/Y`，**不触发 relayout**，所以捏合是连续的。
- 子图层（选框/绘制/文字/二维码）的「图片→视图」线性映射**一行没改**：系统按 View 变换反算触摸坐标，
  放大后画笔仍落在正确像素上（真机验证：整幅下画的箭头，放大后位置与粗细同步正确）。
- 单位冻结保留：缩放不改变已存笔画的像素粗细与字号。
- 手势仲裁：`content.onInterceptTouchEvent` 里 `POINTER_DOWN` 即接管（子层收 CANCEL，绘图层丢弃当前笔），
  并且**必须在拦截层喂 `ScaleGestureDetector`**——拦截后 `POINTER_DOWN` 不再进 `onTouchEvent`，
  否则检测器拿不到初始跨度，双指只剩平移。`onTouchEvent` 里跳过 `POINTER_DOWN` 避免重复建立跨度。
- 工具栏锚点缓存加入画布偏移与 `zoom`：缩放/平移后选区屏幕位置变化会重算，不再停在旧位置。
- `applyCanvasBase` 在布局后再跑一次 `applyTransform`，并监听 `content.onLayout` 重算——
  `content.left` 的居中偏移要等 layout 完成才有值，否则会重复计入 translation 导致画布整体跑偏。
- 移除 `canvasFitToggle` 与 `ScreenshotCanvasFit.Mode`；首次打开长图提示「双指缩放可看细节，双击在整幅与满宽之间切换」。

## 12. 二级栏：可拖动 + 显眼收起/展开（22:50）

用户口径：二级工具栏（详细栏）不能拖、默认没贴着主栏；需要收起/展开，默认展开，收起按钮要明显。

### 实现
- **头部条**（`secondaryHeader`，36dp，插在面板 index 0）：
  - 左：`⋮⋮` 拖动把手（整条头部都可拖）；
  - 右：蓝色「收起 ▾」（圆角底、12sp、30dp 高，放在最容易点的右上角）。
- **拖动**：头部 `setOnTouchListener` 记录 `rawX/rawY` 基准，实时写 `secondaryManual` 并 `placeControls()`；
  位置夹在安全区内，`detailWidth≈屏宽` 时水平可动范围很小，实用方向是上下。
- **收起**：`secondaryCollapsed` 只影响可见性——面板 GONE、主栏下方出现「详细设置 ▴」（同「显示选择栏」的锚点），
  点它回到面板；再次展开会清空 `secondaryManual`，回到「贴着主栏」，不会留在被拖走的位置。
- **默认展开**：`selectDrawing()` 里工具变化时重置 `secondaryCollapsed=false`、`secondaryManual=null`，
  第一次点开永远是展开且贴主栏；同一工具内调样式不会反复弹回。
- **位置**：无手动位置时沿用自动贴合（下沿放不下就贴上沿）；`secondaryManual` 优先。
- 文字编辑面板（`annotationEditor`，`annotationInput==null` 时的那块）也从「固定吊在屏幕底部」
  改为贴主栏：下方放得下接下沿，放不下移到上沿，水平对齐主栏。

## 13. 拖动速度修正（22:56）

用户反馈：拖动图片「太慢」，滑图片不是这个速度。

### 根因
`content` 设了 `scaleX/scaleY`，系统把触摸事件按缩放反算后再分发，所以 `event.x` 是**内容局部坐标**；
而 `translationX/translationY` 是**屏幕像素**。原实现直接 `translationX += dx`，放大 4.25 倍时
每次手势只走 `1/4.25` 的距离，体感就是「怎么拖都拖不动」。

日志实测（修复前坐标关系）：`x=107 raw=540 zoom=4.2467` —— 同一次触摸，屏幕 540，局部只有 107，
比例正好是 zoom。

### 修复
- `translateBy(dx, dy)`：`translationX += dx * zoom`（局部位移 × zoom = 屏幕位移）。
- `onScale` 的锚点：改为 `translation += focus * (1 - next/zoom)`。focus 也是局部坐标，
  原公式又减 `content.left/translationX` 再乘除，属于两个坐标系混用，捏合时锚点会漂。
- `animateZoom` 同理改为 `base + focus * (1 - value/start)`，默认焦点换成内容中心
  （`content.width/2`）而不是 root 中心。
- 诊断日志降到 `Log.VERBOSE`：INFO 级每帧一条 IO 会自己把拖动拖慢。

### 实测
```
CANVAS_DY local=-1.833 screen=-7.78 before=-2072.29 after=-2080.07 zoom=4.2467
```
每帧屏幕位移与 translation 变化完全一致（7.78px），帧间隔 8ms → 约 970px/s，1:1 跟手。
（`adb input swipe` 的总位移不代表参数值，用它量距离会误判为「慢」，以这条日志为准。）

APK sha256 `cc3aba48d1cd61fe38025af5c20d2de78b9d9512abf42b68d6f6646f2aa70c75`。

## 15. 惯性滑动 + 吸附移除 + 选择仲裁 + 把手自适应（23:26）

用户四条反馈：①长截图滑动贼慢、要惯性；②滑动在整幅/满宽之间跳来跳去没法编辑；
③编辑过的元素选不中、拖不动；④框选 UI/把手自适应之后太大。

### ① 惯性滑动
- `VelocityTracker` 采速度 + `OverScroller` 衰减；**驱动用 `postOnAnimation` 自循环**，
  不能用 `computeScroll()`——`content` 无背景（`willNotDraw=true`），invalidate 不触发绘制管线，fling 原地不动。
- 到边界（translation 被 clamp 顶住）就 abort，不贴墙打转；DOWN 即打断惯性接住画面。
- 松手阈值 100px/s，上限 10000。双指松手不甩（snapZoom 已删，见②）。

### ② 吸附移除
松手自动吸附会在整幅↔满宽之间来回跳（用户原话"跳来跳去"），**已删除**。
停在任意比例都可以，档位切换只靠双击显式触发。

### ③ 对象选择与画布平移的仲裁
- 根因：SELECT 的 `selection.press/move/release` 总是消费事件，空白处拖动既选不中对象也平移不了画布。
- 改法：SELECT 按下时若 `selected==null && tapCandidates.isEmpty()`（什么都没点到），
  本次拖动经 `drawing.onCanvasPan` 回调转发为画布平移（屏幕像素增量）；
  点到对象则维持原选择手感（拖动/缩放/删除）。`content` 的 `canPanCanvas` 收紧为 `tool==null`，
  两条路径互不抢。
- 打开工程时 `activeTool` 为空 → 工具保持 null（此前强制 SELECT）——打开长图第一件事是滑动浏览。

### ④ 把手/UI 尺寸自适应
- 选框把手（8dp 白方块）、文字标签、触点判定半径原本是"屏幕 dp 换算成图片像素"，
  画布放大后跟着放大，4.25× 时看起来巨大。
- `ScreenshotDrawingLayer` 新增 `viewZoom`（`applyTransform` 每帧同步），`unit`/`slop` 除以 `viewZoom`，
  把手在屏幕上保持恒定大小；触点命中半径也随之收紧，放大后点选更准。
- 双指平移顺带修了同一处坐标系数（focus 增量 × zoom）。

### 验证与说明
- 无吸附：滑动停在中间比例不再跳回整幅（真机）。
- 惯性：逻辑路径经日志确认（`CANVAS_FLING` 到达并启动 OverScroller）。
  **`adb input swipe` 事件稀疏（150ms 只有 2 个样本），`computeCurrentVelocity(1000)` 采到 0**，
  无法用它量惯性；真人手指每 8ms 一个样本，采样正常，需真手验收。
- 上一轮"松手不甩"的直接原因也查清：测试点落在箭头对象附近，被 SELECT 命中逻辑吃掉——③修好后空白滑动才走得通。
- APK sha256 `5f6ffbc1914f97821246b520e220a1f414c8c2f985275d642e75b671af6d9989`。

## 16. 缩放/拖动抽搐与重影（23:32）

用户反馈：双指缩放+双击之后移动"鬼畜"、放大有重影、缩放不跟手、拖动抽搐。

### 三个根因
1. **clamp 分支跳变**：`applyTransform` 里 `scaledW <= 视口` 时强制居中、`> 视口` 时贴边——
   缩放跨过"内容恰好占满视口"的临界点时，每一帧都在两个分支间切换，画面位置跳来跳去。
   改为**连续区间**：内容边缘的屏幕位置被限制在 `[min(0,视口-内容), max(0,视口-内容)]`，
   跨临界点平滑过渡；初始居中改为一次性显式定位（`canvasPositioned`）。
2. **手势中整栏重排**：`applyTransform` 每帧调 `placeControls()`，它要 measure 二级栏两次并
   `requestLayout`——60fps 下每帧全量重排就是抽搐；掉帧时旧帧留在屏幕上就是用户说的"重影"。
   改为 `gestureActive` 期间跳过（工具栏在拖动/缩放/惯性中保持原位），手势结束（UP/fling 结束/
   双击动画结束）统一 `placeControls()` 一次。
3. 双击动画期间同样进入 gestureActive，动画结束才重排。

### 真机验证
双击放大 → 拖动 200px → 画面 1:1、无重影、无错位（`.android/verify-1113/p1.png`）；
关闭后圆弧恢复。**多指连续缩放的手感仍需真人验收**（adb 无法模拟双指连续事件）。

APK sha256 `3dd00413eb2f2b7d227de456d24a4f5ed8a4cb45f762489ada84eca9fceb8c03`。

## 14. 编辑界面去掉「整个屏幕」的痕迹（23:05）

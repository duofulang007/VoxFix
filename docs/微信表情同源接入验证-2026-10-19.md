# 微信表情同源接入验证

2026-10-19。用户要求微信 App 内同一搜索源，已明确拒绝未经同源验证的腾讯表情替代源。本轮先做只读验证，不改变当前搜狗搜索实现。

第二轮（同日 21:30 起）补做了搜索路径定位与匿名可达性实测，结论见文末[第二轮](#第二轮同日-2130路径定位与匿名可达性)。

## 已取得的证据

1. K60 安装的微信是 8.0.76 / versionCode 3141。只复制安装包代码到本机排除目录，没有读取微信账号、Cookie、聊天数据库或私有应用数据。安装包 SHA256：`04792eb19a566395a9fabee9a50be80245826cb774ec64637a22f7f28acd4054`。
2. 安装包 DEX 中有 `/cgi-bin/mmsearch-bin/emojichatsearch`，反汇编确认构造器 `xv4.l1` 将该路径交给微信 `modelbase` 网络层，请求类型 4384，请求/响应对象继承微信 Protobuf 类型。另有 `/cgi-bin/micromsg-bin/mmsearchemotion`，在 `com.tencent.mm.plugin.webview.emojistore.c` 中使用，请求类型 234。路径和类存在，不等于已确认用户截图的实际搜索调用，更不等于已有可独立调用的 HTTP API。
3. 开源项目 [VellumStyle](https://github.com/CaipingPeng/VellumStyle) 的作者声称使用与微信聊天相同的表情库。核查固定提交 `61463c236755d13b7c64f32ca6afa46e6984cde9` 的 `src-tauri/src/wechat_backend/content.rs`：它在登录后的公众号后台窗口中调用 `POST /cgi-bin/operateremoticon?action=search_all` 和 `action=search_gen`，带后台会话、页面 token 和 fingerprint；普通表情还经过 `action=get_cdn_url` 转换。该源码不能证明公众号搜索与手机聊天排序、覆盖范围完全一致。
4. 对 `https://mp.weixin.qq.com/cgi-bin/operateremoticon?action=search_all` 只做两次无 Cookie 的搜索探测：不带来源头返回 `ret=200004 / invalid referrer`；补齐公众号正常来源头后返回 `ret=200003 / invalid session`。没有尝试绕过登录。这条路线当前不能作为匿名免费接口接入输入法。
5. 用户已确认在微信聊天表情搜索中手动搜索“熊大”“上班”。操作前后只读四个表情搜索组件标签的 Android 日志，均没有输出。没有清日志；无输出不能证明搜索未发生或接口不存在，不能据此断言两次搜索用了上述哪一个接口。

## 继续验证：输入法协作通道

同日进一步检查同一 APK 的声明清单和代码：

- `com.tencent.mm.plugin.emoji.provider.EmotionContentProvider` 明确 `exported=false`；`EmojiStoreSearchWebViewUI` 也是 `exported=false`。已检查的表情 Activity 没有对外搜索结果回传入口。这不足以断言微信不存在其他内部能力，但不能将这些组件当成输入法可直接访问的 API。
- `classes12.dex` 的 `r55.j` 是微信输入法私有命令分发器。其初始化的命令集合有 `send_big_emoji`、`send_message_emoji`、`send_img`、`verify_identity`、`verify_identity_token`、`check_identity_token`、`verify_file` 等，没有表情搜索命令。回传通道是 Android `InputMethodManager.sendAppPrivateCommand`。
- 该分发器会获取当前输入法包名，与 `com.tencent.wetype` 比较，并包含包签名摘要检查分支；另一分支检查身份令牌及有效期。这是“存在身份校验”的代码证据，不代表已在真机尝试或绕过。没有向微信发送私有命令、读取运行时令牌或冒用包名。
- `xv4.s1.a()` 将查询参数写入 `a65.jc7` 请求对象，再由 `xv4.l1` 交给 `modelbase.m1.dispatch`。进一步定位参数构造不能消除其网络会话依赖；尚未获得匿名可调用的请求。

上述检查排除了“直接复制微信键盘协作代码即可得到搜索结果”这一省事方案。进一步无需改日常手机环境的候选是公众号后台：用户自己扫码正常登录后，仅手动对照“熊大”“上班”等词的前排结果与图片标识。已询问用户是否有可用后台账号。对照通过只支持所测词的观察结论，不能证明所有查询和排序长期相同；未验证前不替换当前图源。

新增本机证据：`.android/wechat-search-probe/manifest.xml`、`ime-integration-strings.json`、`network-and-ime-command.txt`、`wxime-classes.txt`、`xv4-s1.txt`。均为安装包静态资料，不含用户运行时会话。

## 接入决策

- 首选仍是经过验证的同源查询接口，加输入合并、取消旧请求、缩略图按需加载和有限本地缓存。缓存用于降低重复请求，不负责证明来源。
- 暂不做全量爬虫或镜像：无法先解决实际查询入口与排序一致性，而且需要额外同步、存储和图片流量。镜像不能自动获得微信的搜索质量。
- 当前不接入公众号登录，不内置账号、token 或第三方微信协议服务，不把 `h5api.sginput.qq.com/wxbq/search` 标成微信 App 同源。
- 普通日志路径现已验证不能提供必要证据。下一阶段若继续，应在独立测试环境中定位搜索请求的构造、鉴权与图片解码，再对同词结果与排序做对照；在环境及操作范围明确前，不修改日常手机证书、VPN、Root、微信安装包或设置。不承诺普通 HTTPS 抓包必然可读微信内部协议。

## 验证边界

本轮无产品源码改动、无新 APK 构建或安装，原搜狗搜索保持原状。尚未完成微信同源搜索的独立请求、结果对照、延迟和流量测量；不能报告图源升级完成，也不能给出未经测量的性能数字。

安装包、DEX、反汇编与匿名响应保存在本机 `.android/wechat-search-probe/`，不提交这些产物或账号信息。

## 第二轮（同日 21:30）：路径定位与匿名可达性

只读静态分析（K60 上 8.0.76 安装包副本）+ 网络探测；未改产品代码，未登录任何账号，未注入触摸。

### 1. 聊天表情搜索实际走两条路径，由服务端配置切换

- **原生容器（WebSearch 插件）**：`com.tencent.mm.plugin.websearch.emojisearch.ui.IEmojiSearchUIComponent` 是搜索界面接口；`dw4.h` 构造 `xv4.l1`，即 `/cgi-bin/mmsearch-bin/emojichatsearch`（reqType 4384）。`xv4.s1.a(a65.jc7, 10, a65.s74, a65.s30)` 把关键词和两枚上下文对象写进 protobuf，再交 `com.tencent.mm.modelbase` 发送。响应父类 `a65.ku5` 带 `BaseResponse`，是标准微信 CGI 报文。
- **LiteApp 半屏**：`SmileyPanelManager`（`com.tencent.mm.view.manager.d`）里有 `startEmojiSearchDialog`、`start emoticon search liteapp`、`preDownloadSearchLiteAppIfNeed`、`preloadSearchLiteAppIfNeed`，由 `MMEmoticonLiteAppOpenApi` 打开 appId `com.tencent.xin.emoticon.tusiji`，带 `appId` / `page` / `halfScreenConfig` 参数。开关是 `clicfg_android_emoticon_search_liteapp`、`clicfg_android_emoticon_search_native_container`、`clicfg_android_emoticon_search_preloadliteapp`。
- `MicroMsg.WebSearch.WxImeEmojiSearchHelper`、`mmkv_wetype_scene_emoji_search` 说明同一套逻辑还与微信键盘协作，但命令分发器里没有表情搜索命令（见前文）。

两条都在微信进程内：前者靠 modelbase 会话，后者靠 LiteApp 运行时和登录态。**不存在“把路径抄出来就能匿名调用”的形态。**

### 2. 匿名可达性实测

- `short.weixin.qq.com`、`long.weixin.qq.com` 的标准 TLS 握手在 ClientHello 后直接 EOF（Python OpenSSL：`UNEXPECTED_EOF_WHILE_READING`），同机 `mp.weixin.qq.com` 正常 TLSv1.3。这两个域名不是普通 HTTPS 站点，走的是 mmtls；`emojichatsearch` 无法用普通 HTTP 客户端构造。
- `mp.weixin.qq.com/cgi-bin/operateremoticon?action=search_all` 带正常 `Referer: https://mp.weixin.qq.com/` 复测，仍返回 `ret="200003"`（invalid session），与上一轮一致。
- `sticker.weixin.qq.com` 是微信表情开放平台（创作者后台），重定向到 `/cgi-bin/mmemoticonwebnode-bin/pages/home` 并要求登录；主页 JS bundle（1.0 MB）里只有 `login` / `home` / `emojioper` / `stikerpage` 等后台接口，**没有公开的表情搜索接口**。
- 微信 APK 原生代码不含 `sginput`、`wxbq`、`operateremoticon` 字面量。注意边界：LiteApp 的 JS 是运行时下载的，所以这条只能证明“微信原生代码不用 h5api”，不能证明 LiteApp 没用，也不能反证它与聊天搜索不同源。

### 3. 于是“严格同源”的可达性

在现有约束（不 Root、不装证书、不登录账号、不自建镜像）下，要拿到与聊天搜索同一请求，只剩两条路，且都被排除：

1. 微信登录态（LiteApp 或公众号后台）——等于把账号凭证放进输入法，不能做；
2. Root + 证书 + mmtls 解密——用户已明确禁止，且仍只是“拿到请求”，不代表能长期稳定复用。

**结论：本阶段无法以低成本满足“微信聊天同源”，卡点是协议与登录态，不是没找到接口路径。**

### 4. 唯一还剩的低成本证据：截屏指纹比对

不改环境也能验证“某个公开源是否与微信首屏同图集”：

1. 用户在微信聊天表情搜索里搜一个词，停在结果页（不发送、不添加）；
2. 电脑侧 `adb exec-out screencap -p` 只读截屏（不注入触摸、不点按）；
3. 把首屏格子与候选接口同词结果做 8×8 aHash 比对：命中即同图集证据，零命中即排除。

这只能证明“所测词的首屏同图”，不能证明全量索引与排序一致；但在不登录、不抓包的前提下，这是唯一能拿到实证的方法。未取得截图前不替换图源。

### 5. 现状与候选源的实测差异（不构成同源证明）

同词首屏 15 张（`.android/wechat-search-probe/quality/`，本机图，不提交）：

| 词 | 现用搜狗 | 腾讯 h5api (sginput) | JSON 体积 / 耗时 |
|---|---|---|---|
| 熊大 | 15 张里多张为不相关白兔，首图带第三方水印 | 15 张全部为熊大相关，含 GIF | 9.1 KB / 153 ms |
| 上班 | 15 张可用，偏实拍梗图 | 15 张可用，偏贴纸字图 | 8.5 KB / 213 ms |

搜狗同两词为 142–145 KB / 236–352 ms（整页 HTML）。两源首屏 aHash 最近距离 12–32（64 位中 0 为同图），**没有一张相同**，说明它们是不同索引，不能互相冒充。体积与时延只说明工程差异，不作为同源依据。

### 6. 截屏指纹实测：两个候选源都被否证

用户在微信聊天表情搜索里搜「熊大」并停在结果页。电脑侧只读 `adb exec-out screencap`，未点按、未发送：

- 前台 `mCurrentFocus=com.tencent.mm/.plugin.lite.ui.WxaLiteAppTransparentLiteUI`，**这台机器的聊天表情搜索实际走 LiteApp 分支**，不是原生容器那条 `emojichatsearch`。
- 方法：裁出首屏 8 格（4 列 × 2 行），去白边后缩到 64×64 灰度、零均值单位化，算相关系数。正控：同一张图嵌进同尺寸白底 = **1.000**，JPEG q60 重压 = **1.000**，两张不同图 = **−0.10 ~ 0.30**。
- 结果：腾讯 `h5api.sginput.qq.com/wxbq/search` 连取 10 页共 **195 张**，与 8 格最高相关 **0.771**；现用搜狗 46 张最高 **0.767**。**没有一格命中同一张图**。逐格对照见 `.android/wechat-search-probe/quality/wechat-vs-tencent.png`、`wechat-vs-sogou.png`。
- 内容形态也不同：微信首屏 8 张是无文字的角色静帧，h5api 首屏是带字幕的梗图模板。
- 结论：**`h5api` 的 `wxbq` 与搜狗图片都不是微信聊天表情搜索的图集**（至少「熊大」首屏）。用户此前拒绝替换是成立的，后续不应再拿它们冒充微信源。
- 边界：只测一个词的首屏，不能排除更深页偶然重合；但首屏不同已足以否定“同一搜索”。
- 隐私：含聊天标题与背景的原始全屏截图已删除，仅保留搜索面板裁图 `wechat-search-熊大.png`。

### 第二轮决策

- 不改图源、不改代码；当前仍是搜狗，界面已如实标注。
- 不接入公众号登录，不把 h5api 写成“微信同源”。
- 截屏比对已给出**否证**：h5api 与搜狗都不是微信首屏图集。同源路线到此收尾，不再尝试匿名复用；若以后仍要提升图源质量，只能作为“明确的非微信源”另开决策，并保留来源标注。

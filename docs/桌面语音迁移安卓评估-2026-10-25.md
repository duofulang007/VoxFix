# 桌面语音整体替换安卓：隔离评估

日期：2026-10-25。目标是替换语音内核，不是仅给现有二遍换权重。长按空格、松手停止、上滑取消、输入框保护及键盘界面继续采用安卓实现。词典内容以后迁移；不搬录音、转写历史、训练工作台或 Windows 窗口/快捷键/送字代码。

后续已完成[实时模块与VAD验证](桌面语音实时模块与VAD验证-2026-10-25.md)，并按用户授权[接入安装主包](桌面R5语音接入与安装-2026-10-25.md)。下文保留第一轮的测试条件和结果。

## 本轮边界

只安装测试 APK，使用已安装主包的当前 SpeechEngine 作基线；没有覆盖主 APK、生产模型、个人词库或剪贴板。设备为 K60 `6959dba1`，主包安装时间在测试前为 2026-10-25 15:42:37。

本轮是**运行可行性与规则对照的第一道检查**，不是完整安卓语音模块完成或真人体验通过：

- 桌面现行 `app/recognize.py` 直接生成每个固定音频的 VAD 起止点、草稿到达时间和最终分段；没有凭描述重写分段。
- 安卓测试包运行 R5 的真实 ARM64 推理、轻声片段增益、最新草稿覆盖/定稿优先调度、标点与语言保护，按录音原时长等待任务到达。记录的是手机实算结果，不是电脑速度推算。
- Android Kotlin Vad API 未暴露桌面 Python 的 `current_segment.start`。因此**本轮 VAD 到达记录预先生成**，没有测安卓实时 VAD、麦克风采集、增益与 VAD 的在线衔接，也不包含这部分 CPU 开销。完整迁移需要补接口或验证等价的起点追踪。
- 两边词典均为空，不运行热词救援。手机已有词库仍然保留，只是不接入隔离对照。
- 36 条、合计 133.021 秒，取自既有固定测试缓存，含合成/变换语音与公开粤语样本。它们适合检查兼容、回归及速度，**不适合为 R5 作总体准确率排名或替代独立真人评测**。没有重新使用 6257 条封存集选模型。
- 模型加载耗时单列；首字从热模型开始喂音频计时，不含冷加载、长按触发及麦克风启动。PSS 是隔离目标进程回放期间每100ms采样的峰值，不包含 WebView，也不保证捕获加载瞬间峰值。

## K60 已完成结果

各配置单独启动隔离进程，按 `R5四线程 → 当前手机版 → R5两线程` 串行运行。没有控制CPU温度或重复多轮，因此差异不是稳定性能保证。

| 指标 | 当前手机版 | 桌面流程R5四线程 | 桌面流程R5两线程 |
|---|---:|---:|---:|
| 固定音频数 | 36 | 36 | 36 |
| 热模型首字中位数 | 478ms | 667ms | 679ms |
| 热模型首字P95 | 1427ms | 874ms | 886ms |
| 松手首次返回中位数 | 68ms | 112ms | 141ms |
| 松手最终稳定中位数 | 116ms | 112ms | 141ms |
| 松手最终稳定P95 | 222ms | 155ms | 228ms |
| 回放期间隔离进程PSS峰值 | 888.2MiB | 615.2MiB | 617.4MiB |
| 进程累计CPU用时 | 120,990ms | 167,664ms | 123,481ms |

首字统计只含有文字的34条，两条静音都未出字。当前手机版有松手先返回、后续安全修订；表中把首次返回与最终稳定分开，不能拿其68ms首次返回直接对比候选的最终结果。候选使用预生成VAD计划，未计在线VAD开销。

本次候选初始化记录2144ms，基线863ms，但候选同步加载标点，基线延迟加载标点；基线还使用预优化图，候选是R5原始导出。两者初始化工作量不同，且没有清文件缓存，不能按此表述完整冷启动优劣。

四线程候选36条均完成、未观察到队列溢出或崩溃。30秒长句累计推理11,582ms，松手后172ms返回，没有越说越积压。仍有以下差异：

- `这个bug已经修好了`：基线输出“这个放开已经修好了”，候选恢复bug，但在bug后加了句号。
- `这个API返回的是JSON数据`：基线API识别为app，候选API、JSON正确。
- 正常和加噪两条“谢谢”：基线为“谢谢”，候选多出“呀”。需要独立真人短句复测，不能因总体小样本分数较低而忽略。
- 数字：候选遵守桌面ITN关闭、没有手机原有数字格式转换，保留“三点十五分”“两斤”。它与基线的“3点15分”“2斤”不宜按字面计为识别优劣。
- 候选与同一R5桌面参考逐字相同32/36；差异涉及JSON/Apple大小写、粤语“嘅/个”和“谢谢啊/谢谢呀”。跨硬件推理文字并非逐字保证。

直接忽略大小写与标点、尚未统一数字写法的字面完全匹配，基线30/36、四线程候选32/36；**仅作诊断，不作为采用依据或总体准确率结论**。本次四线程CPU用时比基线高约39%，尚无更省电的证据。

两线程与四线程的36条最终文字逐条相同，CPU用时约为基线的1.02倍、四线程的0.74倍；首字中位数仅比四线程多12ms，最终稳定中位数多29ms。**下一阶段以两线程为起点更合适，不直接照搬桌面四线程。** 尚未计在线VAD、采音、词典救援和UI开销，不能据此宣称实际更省电。

结论：同一R5和桌面分段/草稿规则在K60的计算量可接受，整体迁移值得继续；主要收益可能是移除第一遍模型、降低内存和改善部分术语。代价是当前首字中位数约慢200ms，以及已观察到短句增字。**本轮通过的是计算可行性检查，未通过完整迁移/日用替换验收，也未证明总体准确率提升。**

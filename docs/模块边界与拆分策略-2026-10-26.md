# 模块边界与拆分策略（2026-10-26）

回答一个问题：现在文件是不是按模块整理的？后面功能变多该怎么防「改一处坏三处」。

## 一、结论

1. **现状不是「按模块整理」，而是「叶子模块已抽净 + 两个聚合层巨石」**。前端 8 个运行时模块依赖关系严格单向、零循环；`app.mjs` 与 `VoxFixImeService.kt` 各自承担全部协调职责，内部无边界。
2. **不建议现在做「整体拆分」**。2026-10-17 的判断（按功能切 `app.mjs` 必循环依赖）依然成立，原因是共享可变状态与单点 `render()` 是横切关注点，不是文件问题。
3. **真正能防「屎山」的是三件事，按收益排序**：行为回归网 → 依赖方向可检查 → 功能只加不改。目录结构排在最后，几乎不影响维护成本。

## 二、现状测绘（2026-10-26 实测）

前端运行时模块（`node tools/check_module_boundaries.mjs` 输出）：

| 模块 | 行数 | 体积 | 依赖 |
| --- | --- | --- | --- |
| `app.mjs` | 2184 | 187KB | 依赖下面全部 7 个 |
| `pinyin.mjs` | 252 | 17KB | 无 |
| `core.mjs` | 198 | 12KB | 无 |
| `lexicon.mjs` | 127 | 10KB | `core.mjs` |
| `voice-orb.mjs` | 99 | 4KB | 无 |
| `meme-search.mjs` | 65 | 5KB | 无 |
| `split.mjs` | 41 | 2KB | 无 |
| `english.mjs` | 12 | 1KB | 无 |

- 依赖图是**严格两层**：7 个叶子模块之间只有 `lexicon → core` 一条边，全部由 `app.mjs` 单向聚合。**没有循环依赖**。
- `app.mjs` **0 个 `export`**，内部 645 处 `state.` 读写、115 处 `render()` 调用——没有任何模块边界可言。
- 原生侧已抽出 20 个单职责文件（`SelectionDrag`/`SelectionNavigation`/`SelectionSteps`/`CursorBoundary`/`HostSelectionRequest`/`InputSession`/`AnnotationOverlay`/`ClipboardSplitState`/`Meme*`×4/`PersonalLexicon`/`VoiceDictionary`/`PinyinEngine`/`VoiceRecorder`/`PcmCapture`/`NativeMemory`），各被 1–6 处引用；`VoxFixImeService.kt` 1554 行 / 49 个成员函数保留生命周期与协调。
- 41 个 `preview/*.test.mjs` 中 32 个是**黑盒**（起 http + `page.goto` + DOM 操作或 `page.evaluate`），**没有任何测试 import `app.mjs`**，只 import `pinyin.mjs` 这类纯逻辑。

## 三、「牵一发动全身」的三个真实机制

不是文件太少导致的，所以拆文件也治不了：

1. **单一可变状态**。645 处 `state.xxx` 意味着任何功能都能改任何字段，没有字段归属。改一个功能时最难判断的不是代码在哪，而是「这个字段还有谁在用」。
2. **单点全量重绘**。115 处 `render()` 意味着任何一个新功能都可能影响别人的渲染路径；`app.mjs` 已经为此打过补丁（页内容与覆盖层分离、`syncPageDrift` 原地抄滑轨标签），说明耦合已经在付利息。
3. **单文件无边界**。2184 行内没有任何「这个函数属于哪个功能」的强制约束，新代码落到哪里全靠习惯。

拆成 10 个文件但共享同一个 `state` 对象、共用一个 `render()`，上面三条一条都不会消失，只会多出 10 个循环 import。

## 四、已经存在的防线（要用起来）

- **回归网**：41 个黑盒测试按功能命名（`toolbar-drag`、`letter-hold`、`selection-lock`、`clipboard-match-ime`…），覆盖的是行为契约而不是内部结构。这条防线最有价值的一点是：**只要 DOM 与交互不变，重构内部结构不会让测试失效**。也就是说拆分不是「没保险」，而是保险免费。
  - 因此规矩是：**改完任何一个功能，跑全量 `preview/*.test.mjs`；新增功能必须新增一条 test.mjs**。没有测试的新功能，等于把风险记在账上。
- **依赖方向可检查**：新增 `tools/check_module_boundaries.mjs`，检查循环依赖、叶子层越层反向依赖、单文件体积红线、以及写了但没接进产物的模块。当前结果：0 越线，1 体积预警（`app.mjs` 2184 行，预警线 2200）。建议纳入每次提交前的自检。

## 五、红线指标（触发才动手，不设一次性重构）

| 指标 | 预警 | 必须处理 |
| --- | --- | --- |
| 单文件行数 | 2200 | 3000 |
| 单文件体积 | 180KB | 250KB |
| 循环依赖 / 反向依赖 | — | 1 处即处理 |
| 一次小改动导致无关测试失败 | 1 个测试 | 2 个及以上（说明边界错了） |
| 新增一个功能需要改动的位置 | 4 处 | 6 处以上 |

判断「无关测试失败」很关键：它比行数更早暴露真实耦合。以前几轮出现过改工具栏影响候选区、改删除曲线影响选区的迹象，都是这个信号。

## 六、分阶段路线

### 阶段 A：零风险，可立刻做（每次 10 分钟量级）
纯逻辑继续下沉到叶子模块。当前 `app.mjs` 里仍有一批纯函数（`NEIGHBOR_KEYS`、`PINYIN_FINALS`、`nearbyPinyin`、`firstSyllable`、`holdPopupGeometry`、`characterCount`、方向表与几何换算），不碰 DOM、不读写 `state`，搬进 `pinyin.mjs` / `core.mjs` 后行为完全等价，黑盒测试直接验证。
→ 单次收益不大，但它是「改动顺手做」的模式，累计 3–5 轮后 `app.mjs` 会明显瘦身。

### 阶段 B：结构性，需要设计一次（加新功能前做最划算）
给 `app.mjs` 引入**功能模块登记**，把「改巨石」变成「加文件」：

```
preview/features/<name>.mjs
  export const keys = ['clipGroup', 'clipManage']   // 该功能独占的 state 字段
  export function paint(ctx)                        // 只产自己的 DOM 片段
  export function onAction(action, ctx)             // 只处理自己的 data-action
```

`app.mjs` 只保留三件事：状态容器、`render()` 按登记表顺序拼装、事件委托按 `data-action` 查表派发。

前置条件（不做就会造出第二套框架）：必须先有 `ctx` 的明确契约（可用 state 子集 + 挂载点 + 动作注册），并且**只迁一个功能试水**（建议 `meme-search` 或 `phraseGroups`），跑通全量测试后再迁第二个。

### 阶段 C：原生侧（成本最低，收益确定）
`VoxFixImeService.kt` 的 49 个函数按职责分四簇：选区协调、语音上屏、剪贴板与面板、渲染与几何。Kotlin 有类型和显式接口，抽类比 JS 容易，且已有 20 个模块的成熟做法可参照。
→ 顺序建议：语音上屏（与选区耦合最浅、已有 `DesktopSpeechEngine` 接口）→ 剪贴板/面板 → 选区协调。

## 七、登记点（打包脚本已于 2026-10-26 改为零登记）

**新增一个 `preview/*.mjs` 现在要改 3 处**：

1. `preview/xxx.mjs` 本身（写代码）
2. `preview/app.mjs` 的 `import`（不 import 就不生效）
3. 对应 `preview/*.test.mjs`（新功能必须配测试）

**不再需要**改 `tools/build_preview.py`：该脚本已从「硬编码模块清单 + 手工拼接顺序」改为**从 `app.mjs` 的静态 import 图做拓扑排序自动拼接**（依赖在前、入口在最后），新增模块零登记。历史上漏内联 `lexicon.mjs` 导致整页不渲染的问题随之消失。

脚本现在的三个安全网：

- 遇到循环依赖直接报错退出（`app.mjs -> x.mjs -> app.mjs`），不会静默拼出错序产物；
- 拼接前按状态机剔除 `import` 语句与行首 `export `，支持跨行 import；有未闭合 import 会报错；
- 拼接后再扫一遍残留的 `import` / `export` 行，出现即报错，避免新写法（如 `export{}`、`export default`）被悄悄漏掉。

改造的验收方式：用原手工清单重建的产物与新产物 **sha256 完全相同**（13,449,700 字节），即零行为变化；另外用临时探针模块验证了「只加 import 就能被打包」与「循环依赖被拦下」两条路径。

日常构建一条命令：`python tools/build_preview.py`（约 0.4s，内容未变时跳过写盘）。**由 agent 在改完后自己跑，不转交给用户。**

**开发时看效果不需要打包**：直接开 `preview/index.html` 走本地 http（41 条测试也是这么跑的），单文件 `键盘试用页.html` 只用于分发（双击即开、无需服务器）。

> 曾实现过 `--watch` 监听模式（0.6s 轮询、改动自动重建），2026-10-26 按用户要求删除：规则已改为「agent 改完自己跑一次」，用户不需要挂任何进程，监听模式属于多余的维护面。将来真需要，再加约 20 行即可。

## 八、不做清单

- 不按「目录好看」拆：把 `app.mjs` 平铺成 `render.mjs` / `handlers.mjs` / `painter.mjs` 这种按技术分层切的文件，只会制造循环依赖。
- 不做一次性大重构：41 条黑盒测试能保护行为，但保不住一次性改 2000 行的可审查性。
- 不引入框架（React/Vue 等）：现有 41 条测试全部基于当前 DOM 结构，换框架等于重写测试网。
- 不为了并行而拆：真并行仍是 worktree + 分支，拆文件不解决冲突，只降低冲突面积。

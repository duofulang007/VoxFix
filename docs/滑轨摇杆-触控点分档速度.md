# 底部滑轨摇杆：以触控点为原点的三档速度

2026-10-13。用户报：滑轨必须**滑到左右边缘**才能持续移动，希望改成「以触控点为原点、按到原点的距离分三档速度，整个区域都要有效」。

## 旧行为

`core.mjs` 的 `cursorEdgeRate(width, x)` 只在 `min(x, width-x) < min(48, width/4)` 时返回非零，
即**必须贴着滑轨两端**才进入自动续移，档位 20 / 10 / 4 步每秒。滑轨中段怎么拖都只跟手、不续移。

## 新模型：跟手基线 + 速率叠加

关键不是「用速率替换跟手」，而是**叠加**：

```
发送步数 = trunc((lastX - 按下点) / 11)   ← 跟手基线，任何时候都有效
         + 速率累加步数                    ← 只在超出内圈后叠加
```

这样做的直接好处是**整片区域不会有盲区**：原点之外任何位置都有输出（跟手始终在算），
速率只是在外面再叠一层加速度。同时手指推回近处时速率自然归零、跟手继续接管，**不会跳变**。

方向只取水平分量 `Math.sign(dx)` —— 文本光标本来只能左右走，垂直推力只用来「更快」，不用来决定往哪走。
`dx === 0` 时速率不生效（纯垂直推没有方向语义）。

## 分档参数（`core.mjs` 的 `joystick`）

| 量 | 值 | 说明 |
|---|---|---|
| `shape` | 3 | 超椭圆指数 n，见下节 |
| `gates` | `[0, 0.78]` | 档 0/1 的下界（归一化 ρ） |
| `rates` | `[0, 24]` | 对应的字/秒；档 0 是跟手位移（速率 0） |
| `hysteresis` | 0.06 | 降档阈值比升档低 0.06，防在边界抖档 |
| `minSide` / `minUp` / `minDown` | 60 / 90 / 40 | 半径下限（CSS px），**上下分开**见下节 |

**只分两档**：绝大多数区域是「跟手」（手指移多少、光标/选区就动多少，能精确定位到某一行），
只有推到最外圈才切高速。三档版本（门槛 0.42 / 0.72）门槛太低——向下可用空间只有几十像素，
推 23px 就进 8 字/秒，手感就是「稍微动一下就跨行」，无法精准定位。门槛提到 **0.78** 后短距离推不出速率。

- 归一化半径 `ρ = ( |dx/a|ⁿ + |dy/b|ⁿ )^(1/n)`，`n = 3`。
- **`ρ ≥ 1` 只是「钉在最高档」，不是「停下来」**。滑到键盘最右上角照样以 22 字/秒 走。
- 唯一的零速率点是**触控点本身**。跟手基线按 11px/字 走，天然带来 ~11px 的死区，不需要额外死区参数。

真机几何（滑轨半宽 ≈ 131 CSS、到键盘顶 ≈ 329 CSS、到键盘底 ≈ 32 CSS，中心按下）：

| 档 | 横向起点 | 向上起点 | 向下起点 |
|---|---|---|---|
| 0（跟手） | 0 | 0 | 0 |
| 1（24 字/秒） | ≈ 102px | ≈ 257px | ≈ 31px |

向下那格约等于「推到键盘底」，这就是「拖动框最边缘最快」的落点。

## 为什么不是正方形，也不是正圆

两者是同一个超椭圆公式的两个端点：`n=∞` 是正方形（切比雪夫距离）、`n=2` 是圆/椭圆。

**正方形**沿 45° 推要走到 `a√2`，也就是**多走 1.41 倍物理位移**才进同一档 ⇒ 斜向明显迟钝。用户要的是二维
（框选要斜着拖），这个迟钝会实打实被摸到。

**正圆**各向严格一致，但键盘是矩形，`ρ` 到 1 时离角落还有 41% 的距离，角落被白白浪费。

`n=3` 的圆角方在两者之间：斜推衰减约 11%，人基本分辨不出来，同时角落照样能推满。
`a`、`b` 由**按下瞬间的可用空间**决定（见下），所以纵向自动比横向长——向上空间本来就更大。

## 实现要点

- **半径在 `pointerdown` 那一刻锁死**：`joystickRadii(side, up)`，其中 `side = min(到滑轨左边缘, 到右边缘)`、
  `up = 到键盘顶的距离`。原点始终是触控点，靠**收缩半径**适配贴边位置；否则在滑轨最左端按下时向左永远推不到高档。
  不能每帧重算，否则手指一动半径就变、手感会漂。
- **速率循环必须 rAF + 累计器**：8 字/秒 ÷ 60fps = **0.13 步/帧**，直接 `trunc` 永远是 0，光标会一动不动。
  小数必须攒着（`g.joy.acc`）。
- **`dt` 夹到 50ms**：Android WebView 切后台回来时 rAF 会跳一大帧，不夹会瞬间冲出去几十个字。
- **`rate` 变化时才重置 `ts`**，避免把 `rate === 0` 的那段时间算进 `dt`。
- 收尾：`endGesture` 里 `cancelAnimationFrame`；进入框选（`g.selecting`）时循环自行退出。
- 原生侧**零改动**：`gestureMove(steps: Int)` 收的是相对锚点的绝对步数
  （`VoxFixImeService.kt` 里 `navigateSelection(steps - cursorSteps, 0); cursorSteps = steps`），
  速率循环只管往上加 `steps`。上一轮修的 `canStepCursor` 每步封边界这里直接复用，推到文本首尾不会把焦点送出去。

## 上下半径必须分开（否则正下方推不动）

滑轨贴着键盘底。以触控点为原点实测：**向上有 ~329 CSS 可用，向下只剩 ~32**（键盘底就是屏幕底）。

共用一个半径时，正下方推满也只有 `ρ ≈ 32/329 ≈ 0.1`，落在跟手档 ⇒ **往下拖等于不动**；
而斜下能推，是因为水平分量在撑 `ρ` —— 用户看到的就是「只有底下左右两边才能用」。

所以 `bUp` / `bDown` 分开取（`dy < 0` 用 `bUp`），`minDown = 56` 让向下推 25px 左右就能进速率档。
向下到不了最高档是物理限制（手指滑出屏幕收不到事件），但"能往下拖"必须成立。

## 框选（长按 350ms 进入）也走同一套三档

框选原本是 `updateSelectionEdge`：**只有把手指拖到选区边缘 18px 内**、延迟 400ms 才续移（和移光标的贴边续移是同一套毛病）。一并被摇杆取代：

- **原点是「长按激活点」，之后不再变。** 别跟着手指走——`selectionReady`（上移就位完成）一度把原点重设成手指当前位置，
  结果手指一停 `ρ` 立刻回 0，选区又变回「不动就不扩展」，正是要解决的问题。
- 框选是二维的，所以方向取**单位向量**、两轴同时推进：
  `extraX += ux·rate·cursorStep·dt`、`extraY += uy·rate·selectionRowStep·dt`。
- **`selectionReady` 里必须补一次启动**：「垂直向上拖」的那步 `pointermove` 会走 `lifting` 分支提前 `return`，
  不在这里启动 rAF 就永远不会持续扩展。
- `voxfixSelectionBlocked` / `voxfixReset` 两个原生钩子改调 `haltJoystick()`。

## 验证

- `preview/core.test.mjs`：新增 12 条纯函数断言（触控点零速率、越界仍最高档、迟滞升降档、半径下限、
  圆角方斜推衰减 < 15%）。
- `preview/native-ime.test.mjs`：把「贴边越近越快」的旧断言改成「离触控点越远越快」（按滑轨半宽的 0.5 / 0.95 取样）。
- `preview/selection-drag.test.mjs`：修掉一个被速率档暴露的**竞态**——原断言把 `selectionStart` 与 `selectionEnd`
  分两次读，而摇杆下光标一直在动，两次读取之间又走了一步（实测 199 → 200）。改成同一次 `evaluate` 读取，
  并把「松手后停止」也改成松手后取基线再比。
- 全部 15 个非真机套件串行通过；`selection-drag` / `selection-direction` 各复跑 3 次稳定。
  （`*-device.test.mjs` 与 `live.test.mjs` 需要真机 / 外部润色服务，不在本轮范围。）

## 未验 / 待定

- **真机手感未验**：本轮只改了打包进 APK 的前端源码，未构建、未安装。按项目铁律「构建 ≠ 安装 ≠ 真机通过」，
  需要在 K60 上实测三档速度是否合适（尤其 22 字/秒 对长文本是否偏慢）。
- 触控点到滑轨左右边缘的**实际距离**没量过，`minSide = 60` 是按「滑轨宽约 295」估的；真机测量后可能要调。
- 档位目前**没有视觉反馈**（仍是原来的 `.cursor-contact` 小灰条 + `.cursor-focus` 光斑）。
  如果用户摸不出自己在第几档，可以加一个随 `ρ` 变大的环。

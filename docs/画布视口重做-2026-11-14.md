| 编号 | 根因 | 代码位置 | 用户感知 |
| --- | --- | --- | --- |

## 2. 三个结构性决策

### 2.1 视口以「视图坐标」为唯一口径，锚点数学用一条式子

`ScreenshotViewport` 持有 `scale / offsetX / offsetY`，语义固定为：

```
screen = offset + (image - contentLeft) * scale
```

`offset` 与 `zoomBy(focus)` 的 `focus` **同属视图坐标**，于是焦点补偿就是
`offset' = focus - (focus - offset) * ratio`，**不需要**任何 zoom 乘数。
旧实现漂移的根源正是两个坐标系混用，不是公式抄错。

`content` 不再做 View 变换，`ScaleGestureDetector.focusX` 天然等于屏幕坐标——这条前提成立，
整个决策才成立（改造后已在真机日志中确认 `off=172.5,694.0` 为居中值）。

### 2.2 渲染改为按屏幕尺度自绘

- 底图：`ScreenshotCanvasSurface` 用 `canvas.drawBitmap(image, srcRect, dstRect, filterBitmap = true)`
  直接从源纹理采样可见区域。长图 1:1 也清晰，不 `createScaledBitmap`、不额外占内存、
  不需要分块解码（整图已在内存时这是分块采样库的等价做法）。
- 标注：`canvas.translate(panX,panY); canvas.scale(scale)` 后用图片坐标画，
  矢量在**最终屏幕尺度**上栅格化。
- 底图与标注合到同一个 canvas：层间错位不可能发生，高亮 `MULTIPLY` 也真正与底图相乘。

### 2.3 画布范围 = 当初框选的那一块

`ScreenshotViewport.contentRect` 限定画布显示的图片范围。编辑已保存的截图时
`contentRect = document.viewport`，整幅比例也按该区域计算——用户看到的就是自己截的那块，
而不是一张陌生的全屏截图。新截图流程相反（必须看全屏才能框选），保持整图。

### 2.4 底图独立成层 + 分块采样（长图卡顿的修复）

用户反馈「长截图编辑的时候很卡顿」，并直接指出架构错误：**截图在保存那一刻就已经定下来了，
编辑阶段只是在它上面加减标注，底图不该每帧重算**。这个判断是对的。

`dumpsys gfxinfo`（4.2× 放大、连续 5 次滑动）：

| 版本 | 50th | 90th | Janky | Slow bitmap uploads |
| --- | --- | --- | --- | --- |
| 底图与标注同层、整图采样 | 250 ms | 300 ms | 12/12 | 12/12 |
| 分块采样（仍在同层） | 93 ms | 105 ms | 20/20 | 20/20 |
| **底图独立成层 + 分块 + 贴边不重绘** | **10 ms** | **12 ms** | 2/19 | **0** |

三处改动，各自对应一个具体浪费：

1. **底图独立成 `ScreenshotBackdropView`**：静态像素只在自己失效时绘制，画标注完全不碰它。
   高亮是唯一例外——`MULTIPLY` 需要与底图在同一 canvas 相乘，跨 View 无法混合，
   所以只有存在高亮对象时，绘图层才自己再画一遍底图（此时才承担成本）。
2. **`ScreenshotTileBackdrop` 分块**：整张 916×10192（≈37MB）作为一张纹理会被 HWUI
   反复驱逐再上传，切 2048 高的小块后一次只触碰可见的 1–2 块。缓存 6 块（≈45MB）
   刚好装下整条长图，滚动时零重建。
   **必须只画「分块 ∩ 可见区域」那一段**——整块直接贴会把画布范围之外的内容也画出来。
3. **视口没变化就不重绘**：`panBy/zoomBy/set` 返回「是否真的变了」。长图整幅显示时
   高度正好等于视口，任何纵向拖动都被边界吃掉，旧实现仍然逐帧重画底图。

另外查出一个非视口的放大器：这条长图记录带 **107 个 FILTER 对象**（长截屏自动打码），
`ScreenshotDrawingRenderer` 的滤镜缓存只有 24MB，装不下全部区域，每帧驱逐重算。
缓存提到 96MB，并让完全在视口外的打码块直接跳过。

### 调试入口（debug 构建）

```bash
# 打开记录
adb shell am broadcast -a local.voxfix.debug.DEBUG_EDIT --es id <32位id>
# 直接把画布放到指定倍率（adb 无法模拟双指，测"放大后滚动"必需）
adb shell settings put global voxfix_debug_zoom 4.2
adb shell settings delete global voxfix_debug_zoom   # 用完删掉，否则下次打开还是放大
# 进程内导出当前画布到 files/canvas-snapshot.png（本机 screencap 对 overlay 会冻结旧帧）
adb shell am broadcast -a local.voxfix.debug.DEBUG_SNAPSHOT
adb exec-out run-as local.voxfix.debug cat files/canvas-snapshot.png > snap.png
```
`run-as ... cat` 必须走 `exec-out`：`adb shell ... cat` 会把二进制当文本做 CRLF 转换，
拉回来的 PNG 头是 `0d0d0a`，打不开。

### 真机踩到的两个坑（记录）

1. `am force-stop` 会把 VoxFix 从 `enabled_accessibility_services` 摘掉，之后 `DEBUG_EDIT` 广播
   「for 0 receivers」、`rebind` 脚本报「不在已启用列表里」。恢复靠手工
   `settings put secure enabled_accessibility_services "local.voxfix.debug/local.voxfix.debug.ScreenTextService:li.songe.gkd/..."`。
2. `screencap` 抓 accessibility overlay 不只是「偶尔取旧帧」——实测连续点击工具栏（`gfxinfo`
   帧数 40→44 在涨）截图字节**完全不变**，那条 overlay 的截图会永久冻结。
   **判断画面一律用 `DEBUG_SNAPSHOT` 的进程内快照，不要再依赖 `screencap`。**
3. `Run-as cat` 取二进制必须走 `adb exec-out`，`adb shell` 会做 CRLF 转换损坏 PNG。
4. 恢复工程与布局的时序：`applyCanvasBase` 可能先于 `restoreProject` 跑过一轮，那一轮
   `picked` 还是 null，画布会被当成整图。必须在 `restoreProject` 之后 `root.post` 再按选区重排一次。

## 5. 待用户真机验收（adb 无法模拟的部分）

1. 双指捏合放大/缩小：焦点下的像素是否稳住、松手是否停在任意比例不回跳。
2. 双击后**不松手**上下拖：连续缩放（QuickScale）。
3. 长图满宽后画 2px 细线：线宽与位置是否随缩放同步，放大后是否清晰（不再发虚）。
4. 单指拖动是否 1:1 跟手、有惯性、到边界停住不打转。
5. 有工具时第二指落下：当前笔画是否被丢弃、是否转为缩放。
6. 从键盘剪贴板点「编辑」的完整路径（含无文字工程、带文字工程）。
7. 保存后列表仍 1 条、再点进去对象还在。

## 6. 已知限制 / 未做

- **工具栏未重排**：仍是「主栏 + 二级栏 + 浮层」的既有结构。`placeControls` 有 400+ 行锚点逻辑、
  `screenshot-toolbar` 设备套件锁定其几何，改成底部固定条必须配真机逐项回归，本轮不动。
  这是「国产标注 App 手感」里唯一未兑现的一项。
- **边缘回弹未做**：`bound()` 是硬夹，无越界阻尼与 settle 动画。要做需要「软边界 + 回弹动画」两个新状态，
  风险高于本轮收益，留待下一批。
- 文字层（OCR 就地编辑）保留了 EditText 真实子 View，其清晰度取决于字号 × 视口比例，
  极端放大时仍是系统字形栅格化，不做额外位图化。
- `ScreenshotDrawing.snapshots` 仍无条数上限（长编辑会话内存线性增长），未在本次范围内。

## 7. 做过又回退的：列表「可编辑」角标

v1 给 `imageCard()` 加过「可编辑」角标（`kind === 'project'` 时），理由是"让用户知道这条能接着改"。

2026-11-14 用户否掉，理由成立：

1. **没有区分度**：每条记录都能点「编辑」（普通图片首次编辑会原地升级为工程），所以这个标对所有条目恒真，等于什么都没说。
2. **盖掉了真正有用的信息**：它是三元表达式里的优先分支，PC 导入的图片编辑过一次就丢掉「电脑」来源标。

已回退为只标来源（`source === 'pc'` → 「电脑」），并在 `clipboard-images.test.mjs` 里钉了两条断言：
PC 来源即使 `kind === 'project'` 也必须显示「电脑」、手机内的记录不加来源角标。

**教训**：给列表加状态标之前先问「它在什么情况下不成立」。恒真的标签只是噪声，
而且三元表达式里新加的优先分支会静默顶掉旧标——加之前要看清楚被替换的是什么。

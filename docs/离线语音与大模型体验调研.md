# 离线语音与大模型体验调研

## 2026-10-11：先保证开口出字、松手快完成

本轮为源码核对和官方资料研究，不改识别、模型或手机。用户已明确优先开口出字、松手快完成，其余大模型功能排在后面。以下“当前”指本轮开始时源码；之后的修复和实际验收应另记结果。浏览器、源码和其他手机的上游演示均不能证明 K60 已通过。

### 当前已有能力与边界

- 原生 IME：16kHz 单声道录音 → Zipformer 实时文字 → 在声学分段或松手时运行 Paraformer 二遍 → 全段标点 → WeText 数字格式 → Android 输入框。输入视图创建时已提前初始化 `SpeechEngine`，应复用既有加载流程。证据：`SpeechEngine.kt`、`VoxFixImeService.kt` 和《开发入口》。
- IME 当前不自动调用 Qwen。独立验证页保留 Qwen3.5-2B Q4_K_M、非思考提示、原文保护与撤销；本地 JNI 使用 CPU、4 线程、2048 token 上下文，每次加载模型并在结束后释放。模型文件 1,280,835,840 字节不等于运行内存。证据：`NativePolisher.kt`、`cpp/polish.cpp` 和《手机端大模型框架》。
- 历史固定文本和指定录音曾约 8～10 秒完成整理，也有 27.266 秒且重复未去除的记录。这些是具体旧场景，不能作为当前普遍速度或准确率；整体去重复质量尚未通过。证据：《手机端大模型框架》对应验收节。

### 优先解决的体验问题

1. **采音、反馈、出字分别量时间。** 当前读取块 `3200/16000 = 200ms`；它是读取粒度，不是总响应时间。官方 sherpa-onnx Android 示例用 100ms 的读取块，说明较小块可复用现有接口试验。降低块大小仍需检查采音连续性和 CPU 负载；Android 明确指出最小缓冲只保证对象可创建，不保证负载下录音平稳。[sherpa Android 示例](https://github.com/k2-fsa/sherpa-onnx/blob/master/android/SherpaOnnx/app/src/main/java/com/k2fsa/sherpa/onnx/MainActivity.kt)、[AudioRecord](https://developer.android.com/reference/android/media/AudioRecord)
2. **二遍识别不能长期挡住采音。** 当前 `finishSegment()` 在录音线程同步运行 Paraformer 解码，期间该循环不读取麦克风。它构成积压风险，尚无证据证明已丢音。先测这个阶段，再用最小调整让采音和分段收尾各自连续工作；二遍候选仍保留现有数字、英文、否定和大幅改写保护。依据为本项目 `SpeechEngine.kt` 的调用顺序。
3. **轻声反馈与识别灵敏度分开处理。** 当前 `RMS × 100` 转整数让轻声的视觉反馈粗糙；`RMS > 0.002` 仅控制是否做二遍，没有阻止音频进入流式识别。扩大动效响应不等于识别更准，降低二遍门限也不等于增强麦克风。项目已使用 Android 为识别调校的 `VOICE_RECOGNITION`，应先保留，只有同一 K60 场景对照才考虑更换采音源。[Android AudioSource](https://developer.android.com/reference/android/media/MediaRecorder.AudioSource)
4. **不要把端点时长当成松手等待。** 项目的 0.8 秒、1.6 秒和 20 秒规则用于分段；上游定义按末尾静音、是否已有非空 token 和句长判断。主动松手走停止路径，源码中的 8000 个零样本是用于尾部解码的输入，不是睡眠 0.5 秒。盲目缩短端点容易增加分段次数和二遍负担。依据：本项目 `SpeechEngine.kt`、[sherpa endpoint 定义](https://github.com/k2-fsa/sherpa-onnx/blob/master/sherpa-onnx/csrc/endpoint.h)。

最小真机指标为：启动请求→实际开始录音、开始说话→首个文字、流式更新间隔、松手→最终提交；分开统计冷启动、连续使用、轻声、正常音量和停顿后续说。收集耗时与错误码即可，不保存日常录音或转写，不新增用户调试面板。这里只定义观测指标，没有承诺毫秒目标已达到。

### 大模型如何更易用、更快、更有效

- **默认输入继续走快速链。** 标点、常见数字格式交给已有专用模块；Qwen 仅在用户确实需要整理、改写等任务时运行。把每段实时文字送给 Qwen 会重复提示处理和生成，且当前去重复质量未通过，不适合立即成为默认输入的必经路径。以后接入 IME 还须核对输入会话和原选区，迟到结果不能覆盖用户后来输入的新内容。此为依据项目状态作出的工程建议。
- **先试短时间复用权重，再试新后端。** llama.cpp 把模型与上下文分为独立对象。可在实际调用整理后短时间保留同一模型权重；每段新建或清理上下文，保留跨次隔离，退场或内存压力时释放。这样只减少反复加载的工作，生成耗时仍需实测。不要用持久会话缓存保存用户转写；静态系统提示缓存也需固定模型、模板和精确 token 前缀。项目现有按次加载已是安全基线。[llama.cpp 模型/上下文/状态 API](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h)
- **保留非思考、短任务与完整输出检查。** Qwen3.5-2B 官方默认非思考，且专门提示该 2B 模型在思考模式可能循环。当前已实现非思考模板与超时，不应当作新增优化；应先评测短任务、输出长度和有效整理率。官方文本采样建议与当前贪心生成不同，可用固定短例对照；这不是已确认的重复失败根因，也不能直接照抄参数，官方亦提示过高 presence penalty 可能混合语言、降低性能。不要用 Qwen3 的 `/nothink` 软开关代替已核对模板。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-2B#best-practices)
- **GPU 作为后续实测选项。** 官方 llama.cpp 支持 Android ARM64，OpenCL 面向 Adreno；其列出的验证设备不能替代 K60 验收。项目固定 llama.cpp 为 `8ae386707bed05f02354dbfc6fa5ee0cf58e5f0f`，当前明确 `n_gpu_layers=0`，未实现 GPU 加速。若研究 OpenCL/Vulkan，需要固定兼容版本，核对 Qwen 架构与 Q4_K 支持，并与现有 CPU 比较正确输出、冷暖首字、总耗时、内存、发热与稳定性；先保留 CPU 回退，不承诺倍数提升。[llama Android](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md)、[OpenCL 支持清单](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/OPENCL.md)、[官方构建说明](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)
- **部署易用性可以单独改善。** 当前模型主要用 USB 放入应用私有目录；未来可增加一次性的系统文件选择导入，核对模型架构、摘要、空间和应用实际可读性，完整复制后再替换旧文件。系统 `ACTION_OPEN_DOCUMENT` 可由用户选定单个文件，无须开放其他应用的数据；不能只验证 shell 可读。模型可用后保持一个整理入口即可，不必暴露线程、量化等设置。[Android 文件选择](https://developer.android.com/training/data-storage/shared/documents-files)、[llama Android 私有文件与 GGUF 元数据示例](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md)。

### 更精准的词汇与结束判断

人名、项目名和英文品牌更适合明确的个人词汇上下文。sherpa 官方热词在推理时生效，不必训练模型，但当前仅支持 transducer 的 `modified_beam_search`，默认 greedy 不支持；项目 Zipformer 有对应路线，Paraformer 二遍不能直接套用同一热词能力。因此需要比较二遍是否把热词改回去以及额外解码负载，不应一开热词就宣称整条链更准。个人词库应由用户明确添加并能查看、删除，不自动保存日常语音。[sherpa 热词文档](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)

上游提供 Silero/TEN VAD，但当前长按录音已有明确启动和结束操作。VAD 是判断哪些片段像语音，不会放大麦克风；其阈值和最短语音/静音时长会改变分段。现阶段先解决采音和同步收尾，再评估是否有必要增加 VAD，避免无收益的新模型与弱音裁切。[sherpa VAD](https://k2-fsa.github.io/sherpa/onnx/vad/index.html)、[Silero 配置定义](https://github.com/k2-fsa/sherpa-onnx/blob/master/sherpa-onnx/csrc/silero-vad-model-config.h)

### 可做但尚未在 IME 实现的功能

以下是基于现有本地文字模型的产品方案，需要各自短文本评测，不能视作已通过。官方模型卡展示语言、翻译、指令、多模态与工具调用能力，2B 的参数规模仍限制复杂任务质量；当前 JNI 只传文字，并未接入视觉或音频输入。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-2B)

| 顺序 | 功能 | 适合输入法的最小形式与边界 |
|---|---|---|
| 先做 | 口语整理、去重复 | 一次处理当前段，保留数字、否定和原文撤销；当前独立页已有基础，但质量不稳定，IME 未接通 |
| 后做 | 改语气、精简、翻译 | 用户选中文字后点一次操作，完成后可撤销；属于有意改写，应与原意整理使用不同的允许变更范围 |
| 后做 | 摘要、清单、待办提取 | 只处理用户提供或选中的文字，不从未授权的其他 App 页面取内容，不编造未说出的事项 |
| 后做 | 说话改文字 | “删上一句”“把这句改简短”先设计独立命令入口，避免把普通口述内容当命令执行；删除和替换可撤销 |
| 另评估 | 私人词库、语气偏好 | 明确保存少量用户选择的词或偏好即可，不等于模型自动训练；不能把每天说话当隐式训练授权 |
| 暂后置 | 截图理解、图片提字、跨 App 自动操作 | Qwen 官方模型带视觉编码器，但项目仅文字 JNI，尚无视觉资产/预处理/权限/操作协议，不因拥有 GGUF 就算已支持 |

本轮来源访问日期为 2026-10-11。上游 `master` 文档用于研究可行性，不能代替项目固定版本的接口和 K60 结果。未运行手机、安装 APK、变更模型、做耗电测试或增加源码；首字、松手延迟和模型质量仍需下一轮真机测量。

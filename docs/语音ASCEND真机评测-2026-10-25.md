# ASCEND 1314 条真机准确率与响应速度评测

日期：2026-10-25；设备：Redmi K60 `23013RK75C`（`6959dba1`）Android 15 / HyperOS；被测包：`local.voxfix.debug` **0.2.0-r5（versionCode 2）已在机**，引擎直接读 APK 内 R5 资产，没有拷外部模型。

按用户要求「和电脑一样跑测试、样本量也一样」，本轮用桌面 `VoxFix Desktop/tools/evaluate_sensevoice.py` 同一份清单 `work/baseline-20261022/manifest-original.json`（**1314 条** ASCEND 真人录音：中文 684 / 英文 257 / 混说 373，合计 3302.3 秒）在手机上重跑，并用桌面自己的评分模块 `p0_score.units/distance/exact` 计分。**不是抽样，不是等价替换音频：1314 条 PCM 逐字节校验桌面记录的 `pcmSha256` 后才解码。**

## 结论

手机端语音与桌面端**基本等价**：整句匹配 654/1314（桌面 653/1314），三类单字错误率差 0.02–0.15 个百分点；逐条 1165 条字节相同、1215 条字级相同，9 条比桌面差、10 条比桌面好，净 +1。两次独立运行（非实时 6 分 06 秒 / 实时节奏 61 分）**1314 条文字完全相同**，链路是确定性的。

响应速度：首字中位 **716ms**、P95 775ms；松手出字中位 **185ms**、P95 680ms。拖后腿的是**长句松手**（6 秒以上中位 608ms、P95 1075ms、最差 1853ms）和**手机被真实使用时的抢占**（松手 P95 从 521ms 涨到 770ms）。

发现两个用户能直接看见的缺陷：语气词位置的 `<FIL/>` 噪声标签没有清洗，会真的打出 `< FIL / >`（1314 条里 125 条）；短于 0.65 秒的句子完全不出字（15 条全是「嗯/对/哦/thank you」）。两者桌面同样存在，不是安卓移植新增的。

| 子集 | 条数 | 首字 P50 / P95 | 松手 P50 / P95 |
|---|---:|---:|---:|

读法：

- 首字几乎不随时长变化（686–720ms），因为它是**固定排程**决定的：桌面/安卓同一套 `MIN_PREVIEW 550ms` + `PREVIEW_STEP 350ms`，到点先出草稿再等定稿。桌面自己测到 618ms，手机多出的约 100ms 是一次草稿段推理差（手机 RTF≈0.11）。
- 松手出字随时长近似线性增长：<1s 106ms，6s+ 608ms。原因是**定稿段串行解码**——一段说完要等上一段解码+标点返回，长句积压 2–3 段就顶到 1 秒以上。
- 空闲时 13 分钟内无热漂移（四分段首字 P50 703→728ms，松手 p50 190→186ms 稳定），不存在跑热了变慢。

## 发现

1. **`<FIL/>` 噪声标签未清洗，会直接打进输入框（用户可见，建议修）**。SenseVoice 对「呃/um/uh」这类语气词输出 `<FIL/>`（还有 `<L/>`、`<IL/>` 及其被标点截断的 `<FIL/`、`<FL？`），而 `DesktopVoiceRules.clean()` 只剥 `<|…|>` 竖线形式，于是 125/1314 条（**9.5%**）文字里残留 `<`、`>`、`/`。手机上因为逐段解码，常见形态是 `So < FIL / > what's your…`。桌面同样中招（原始串 `<FIL/>` 直接留在文本里）。建议在 `clean()` 剥离 `<|…|>` 之后补一条大写标签形态（`<` + 至多 3 个大写字母 + 可选 `/` + 可选 `>`，允许内部空格），并补回归；注意 `p0_score` 忽略符号，**这条不改 CER，只影响用户看到的字**。
2. **短于 0.65 秒的句子完全不出字**。15/1314 条返回空串，全部是 0.17–0.60 秒的单字回复：「嗯」9 条、「对」4 条、「哦」1 条、`thank you` 1 条。桌面**逐条一样是空**，说明是 silero `minSilenceDuration 0.65` + `threshold 0.30` 的下限，不是移植缺陷。但手机上「嗯/对」是高频回复，属于实际体感问题；真要改需动 VAD 参数，会牵连长句切分，建议单独立项并成对回归。
3. **短英文是最弱一档**：<1.5 秒英文 CER 37.19%，明显低于中文同档（13.76%）。桌面 37% 上下，同属模型能力，不是新问题。
4. **长句松手等待破 1 秒**：6s+ 的 P95 松手 1075ms、最差 1853ms。定稿段是串行解码，先说完的段要排在后面段前面解。若要让长句手感跟上，需要做定稿并行或先送已定稿段（会改动送字边界，属功能改动，不是调参）。
5. **真实使用并发时松手延迟翻倍**：同一进程里评测引擎与真实键盘引擎并存时，松手 P95 521→770ms，且进程 PSS 峰值 1.18GB（单引擎回放峰值 634–648MB，含 229MB 识别 + 72MB 标点，不含 WebView）。这是评测与真实使用重叠的观测，不代表日常双引擎；但说明**内存紧张时先掉的是长句手感**。
6. 个别 ASR 层波动：`百分之九十九点九` 在手机上成了 `百分之九十九.九`（桌面是「点」）。手机逐段解码与桌面整段上下文不同，属模型输出差异，规则层没有改字（`punctuate()` 校验不通过会原样返回）。

### 本轮未发现

- 1314 条 × 2 遍零异常、零拒绝：`allowed()` 中英守卫没有触发过（没有日文/韩文误入语料），没有「识别队列积压」、没有 `DesktopVoiceFailure`。
- 崩溃缓冲为空；`am_kill` 只有我方 `start instr` / `finished inst`（第四段中途被一次外部新启动的 instrumentation 顶掉，补跑缺口 77 条后凑满 1314，崩溃栈仍为空）。
- 单实例连续 1314 条无跨条状态泄漏（每条文字与上一遍逐字相同）。
- 没有静音段幻觉出字；没有 VAD 整句漏检（唯一一条「短」是 1.26 秒的 `还有呃so`，两端都是垃圾输出）。

## 边界

- 固定音频回放 ≠ 真人麦克风：不含远场、噪声、口音、真实增益链，也不含跨 App 上屏（宿主、输入框、光标跳动均未涉及）。
- 实时遍的 61 分钟里有约一半时间用户在用手机（打开键盘、起第二个引擎），已单独给出「空闲 / 竞争」两组数字；首字与松手都应按空闲组读数更接近日常。
- 桌面 618ms 首字来自桌面自己的 `--stream-test` 单次记录，条件不是同一批 1314 条，只能作量级参考。
- 未测冷启动（模型加载 2051–2949ms 是热文件缓存下）、未测 3 分钟长录音、未测 NPU。

## 复现

```bash
# 1. 把桌面清单摊成手机端语料（int16 原样，逐条校验 pcmSha256）
.venv/Scripts/python.exe tools/prepare_ascend_eval.py \
  --manifest "D:/Projects/VoxFix Desktop/work/baseline-20261022/manifest-original.json"
# 2. 推到应用外部目录 audio/ 与 plan.json
# 3. 准确率（非实时）
adb shell "am instrument -w -e modelCompare ascend-eval -e evalMode accuracy -e evalOffset 0 -e evalLimit 1314 \
  local.voxfix.debug.test/local.voxfix.debug.VoxFixSmokeInstrumentation"
# 4. 延迟（16k 墙钟，建议分段跑，否则单次 60 分钟以上）
adb shell "am instrument -w -e modelCompare ascend-eval -e evalMode paced -e evalOffset 0 -e evalLimit 329 \
  local.voxfix.debug.test/local.voxfix.debug.VoxFixSmokeInstrumentation"
# 5. 计分（直接用桌面 p0_score）
.venv/Scripts/python.exe tools/score_ascend_eval.py --runs ".android/ascend-eval-20261025/out-paced-*.json"
```

原始数据：`.android/ascend-eval-20261025/`（`out-accuracy-0-1314.json`、`out-paced-*.json`、`score-*.json`，本机忽略目录，不入库）。测试代码：`android/app/src/androidTest/.../DesktopCorpusEval.kt`。

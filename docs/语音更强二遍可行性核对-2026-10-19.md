# 更强二遍与双裁剪批处理可行性核对

核对日期：2026-10-19。只读核查官方资料及当前 AAR；本轮不下载权重、不构建、不装机、不改生产识别配置。本文是评测准备，不是准确率或 K60 性能验收。

## 结论

现有 sherpa-onnx **v1.13.8** 已支持 Qwen3-ASR 0.6B INT8 和 FireRedASR2 CTC，可在隔离测试代码中复用现有库进行模型对照，不必为了试模型先升级依赖。它们是否比当前 SenseVoice 更准、是否赶得上 420ms 替换窗口，都没有本项目同音频/K60 证据。尤其不能拿权重大小推断实际耗时。

优先考虑先验证现有 SenseVoice 的双裁剪批处理：底层已有真正 batch 路径，但当前 Kotlin API 未暴露它，不能直接调用。换模型应排在当前可定位的时序与采用错误之后。

## 固定版本支持证据

- 已逐项核查 [v1.13.8 Kotlin OfflineRecognizer.kt](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/kotlin-api/OfflineRecognizer.kt)：`OfflineQwen3AsrModelConfig`、`OfflineFireRedAsrCtcModelConfig` 均存在；示例配置分别为 type 61、50。Qwen 走 `OfflineRecognizer`，不是现有实时 `OnlineRecognizer` 的替换配置。
- [v1.13.8 JNI](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/jni/offline-recognizer.cc) 对应读取了 `qwen3Asr`、`fireRedAsrCtc` 字段，并创建离线识别器。不是仅有 Kotlin 占位类。
- [v1.13.8 发布说明](https://github.com/k2-fsa/sherpa-onnx/releases/tag/v1.13.8) 包含 Qwen3-ASR/FunASR-Nano 共享 PRNG 数据竞争修复；[同标签 CHANGELOG](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/CHANGELOG.md) 也包含此前 Qwen 静音幻觉、特征对齐修复。不能降到较早版本来试。
- 本地 `android/app/build.gradle.kts` 已使用 `.android/app-tools/sherpa-onnx-static-link-onnxruntime-1.13.8.aar`。本轮只读解压目录结构到内存，AAR 大小 38,691,998 字节，`classes.jar` 确有 `OfflineQwen3AsrModelConfig` 及其配置字段。此检查证明类存在，**没有证明本机 JNI 推理已跑通**。

## Qwen3-ASR 0.6B INT8

这条路线是音频识别模型，与此前移除的安卓 Qwen 文本润色不是同一功能；它仍需独立评测后才决定是否采用。

固定资产：`sherpa-onnx-qwen3-asr-0.6B-int8-2026-03-25.tar.bz2`，官方资产页显示压缩包 **838 MB**，官方发布 API 精确为 **878,702,423 字节**，上传时间 2026-04-07。目录日期不是库版本，也不等于资产上传日期。

- [官方模型压缩包](https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-qwen3-asr-0.6B-int8-2026-03-25.tar.bz2)
- 发布资产 SHA256：`393f8a14e2f5fb96746aaab342997a40641001fbd5bf9592a080a8329178ee96`。来源：[官方 asr-models 资产列表](https://github.com/k2-fsa/sherpa-onnx/releases/expanded_assets/asr-models)。未下载，故未自行验哈希。
- [官方模型页](https://k2-fsa.github.io/sherpa/onnx/qwen3-asr/pretrained.html) 文件表：前端约 42 MiB、decoder 721 MiB、encoder 174 MiB，合计约 937 MiB；另有 tokenizer。文件表是取整显示，不能充当精确字节数或峰值内存。
- [Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-ASR-0.6B/blob/main/README.md) 标明 Apache-2.0；正式分发时保留上游许可、来源与转换说明。压缩包自身的许可文件本轮未解包核查。

Kotlin 隔离测试可使用以下配置，路径必须指向已校验的测试目录；`tokenizer` 是目录，不能传 `vocab.json` 文件：

```kotlin
val config = OfflineRecognizerConfig(
    modelConfig = OfflineModelConfig(
        qwen3Asr = OfflineQwen3AsrModelConfig(
            convFrontend = "$dir/conv_frontend.onnx",
            encoder = "$dir/encoder.int8.onnx",
            decoder = "$dir/decoder.int8.onnx",
            tokenizer = "$dir/tokenizer",
        ),
        tokens = "",
        numThreads = 3,
        provider = "cpu",
    ),
)
```

以上字段依据同标签 Kotlin 源码。它的 `maxNewTokens` 默认 **128**、`maxTotalLen` 默认 512；官方 CLI 常用 512 输出 token，不能混为同一参数配置。初次对照保留默认，无热词基线通过后再单测热词，避免混淆归因。

官方示例日志使用 `/Users/fangjun/…` 路径，是桌面环境；未找到 K60 或 Android 冷启动、峰值内存及 420ms 完成率证据。Android 可调用的 API、示例 APK 与手机交互性能是三种不同证据。不能据桌面 RTF 承诺手机实时体验。

- 对应 Kotlin 配置：`OfflineModelConfig(fireRedAsrCtc = OfflineFireRedAsrCtcModelConfig(model = "$dir/model.int8.onnx"), tokens = "$dir/tokens.txt", numThreads = 3, provider = "cpu")`。依据前述固定标签 Kotlin type 50。

## 现有 SenseVoice 能否批量识别两份裁剪

**底层可以，当前 Kotlin API 不可直接调。**

1. Kotlin 固定标签 API 只公开 `decode(stream)`，没有 `decodeStreams`；本轮核查整个文件而非只看预设。
2. 前述 JNI 文件第 564 行存在 `Java_com_k2fsa_sherpa_onnx_OfflineRecognizer_decodeStreams`，收取 `jlongArray` 后调用 C++ `DecodeStreams(ss,n)`。
3. [v1.13.8 SenseVoice 实现](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/csrc/offline-recognizer-sense-voice-impl.h) 的 `n>1` 分支会为各 stream 做 LFR/CMVN、按最长特征补齐并组成 batch 后运行模型；不是简单循环两次 decode。FunASR-Nano 另有逐条分支，不能泛化。

因此，在不换权重前提下可以做测试专用绑定验证，但需要真正补全 Kotlin 声明与 JNI 调用，不建议反射 native 指针、假定已有方法或盲目并发同一识别器。是否减少耗时、是否提高内存、现有 ONNX 权重对 batch=2 是否正常，必须用原裁剪/补边界同一组数据验证。**本轮未修改或编译绑定。**

## 最小可执行评测门槛

1. 资产进入现有忽略目录；校验压缩包官方 SHA256，解包后记录每个文件 SHA256、尺寸与许可。禁止把模型打进通用 APK/提交。
2. 仅增加测试专用离线识别入口，复用当前 AAR 和固定金标音频。第一组无热词；分别记录模型原始输出、采用后的最终文字。禁止先替换生产 SenseVoice。
3. 同语料对比普通话、否定/金额、英文短词、中英术语、粤语、静音；报告正文 CER/WER、整句匹配及新增退化。更高模型总分不能抵销否定与金额误改。
4. 真机串行测试冷模型加载、热模型单裁剪/双裁剪推理、温度和峰值内存，区分音频结束、首结果、模型完成和最终提交时刻。
5. 采用门槛包含普通输入立即上屏、首结果后 420ms 替换期限与现有引擎迟到等待 600ms（项目现有约束，由主线核验）。超过窗口的正确结果不计交互修复成功；不为新模型擅自延长等待。上述模型均无满足这些期限的官方 K60 证据。

未下载或跑任何新模型，未改生产代码；模型准确率、Android 资源消耗与双裁剪批处理收益均未验证。

# 语音跟手与冷启动优化（2026-10-17）

用户目标：开口后持续出字、音量与动画跟随；松手立即停止收音，后续讲话不进入本段，也不等待较慢的二遍整理。只缓存开头、防漏录不足以满足这个目标。用户询问两种收尾策略的推荐；按其已明确的跟手优先目标，采用立即落字、只使用已完成整理，说明最后一句可能减少标点或数字转换。

## 当前实现

- 原生启动请求放在网页渲染、WebGL初始化之前；第一批真实采样后才显示倾听语音球。复用原有跟手、音量、取消及退场动画，没有新增等待动效。
- `AUDIO_CHUNK_SAMPLES` 从1600降至320，即16kHz下100ms→20ms。采集队列恢复为3秒有界容量，满载PCM约192kB；不以30秒积压代替出字响应。
- `PcmCapture.stop()` 立即停止底层读取，保留此前已采集的队列；同步并幂等处理停止，避免停止与释放竞态。IME桥接在有效WebView上直接请求停麦，先于网页收尾重绘，不等待主线程编辑操作队列。验证页共用入口。
- 停止时读取系统音频时间戳，在可用时按帧位置裁掉跨越停止时刻的采样；时间戳不可用时仍直接调用原生停止。该时间戳是系统估计值，不能据此宣称真实麦克风边界绝对无误，需真人继续讲话验证。
- 流式解码不再同步等待二遍模型或二遍推理。首次流式文字发出后才安排二遍加载；已结束的句段在低优先级单线程后台整理，最多一个等待任务，忙时保留流式文字。`SpeechSegment` 只读取已完成结果，仍经过既有数字、英文、否定与编辑距离保护。
- 松手后处理已采入的尾音并结束，不新开最后一句的二遍任务，也不等待未完成任务；丢弃迟到的整理结果，防止覆盖用户接下来的输入。句末基础标点沿用原规则，最后一句的完整逗号和数字格式不保证。
- 原生推理调用若已开始，允许后台安全退出；不强制销毁仍被调用的模型。普通打字不预加载，保留空闲30秒释放。

后续默认数字修复已在统一输出处完成明确时间、金额和计量转换，不依赖最后一句二遍；此处原先数字格式不保证的描述仅适用于修复前和未覆盖的歧义表达，见[数字专项](语音数字转换专项-2026-10-17.md)。

## 真正减少模型初始化

`tools/prepare_streaming_models.py` 在构建机使用已安装并固定的 ONNX Runtime 1.31.0，提前执行CPU Extended图优化，不启用桌面布局优化。原始三份模型仍保留，按 `tools/setup_voice.py` 的固定SHA-256校验；生成物仅放在忽略目录 `.android/streaming-optimized/`。

脚本校验优化前后输入、输出及模型元数据相同，输出记录哈希；命中缓存时再次验证。Gradle在打包前执行，APK内同名流式模型改用优化结果，不额外打包原始模型。依赖见 `tools/streaming-optimization-requirements.txt`；尚未安装的环境先用项目Python安装该文件中的固定构建依赖。该工具不在手机运行，不修改用户词库、学习或录音。

手机实际初始化仍会随负载波动。最初隔离探针中原APK资产初始化498/505ms、预优化文件349/358ms，二者加载路径不同，不能把全部差值算作图优化收益。最终同一延迟测试包对比旧/新APK内模型的冷初始化，20ms场景为527→430ms；另一次连续对照初始化为516～611ms，优势不稳定。采用的是同一组原始模型，没有更换识别词表或训练新模型，不承诺固定提速百分比。

依据：[ONNX Runtime离线图优化](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)、[sherpa-onnx v1.13.8加载入口](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/kotlin-api/OnlineRecognizer.kt)、[Android录音与时间戳](https://developer.android.com/reference/android/media/AudioRecord#getTimestamp(android.media.AudioTimestamp,%20int))。原始编码器元数据为 `T=39`、`decode_chunk_len=32`；20ms采集不代表模型每20ms都能确定一个字。

## K60固定音频测量

测试不打开麦克风、不操作输入框。`VoiceLatencySmoke` 按真实时间投递已有公开固定音频；先在旧安装版、再在最终版运行同一个测试包。每组首遍为模型对象未加载、次遍复用对象，不代表重启手机后的磁盘冷缓存。包含原始4秒、去掉开头600ms静音区后的4秒、完整10.053秒及20ms投递四种场景。不是日常录音或真人验收。

同一20ms投递场景的本组读数：

| 指标 | 原安装版 | 最终版 |
|---|---:|---:|
| 冷初始化（流式+VAD） | 527ms | 430ms |
| 冷启动到首次文字 | 558ms | 470ms |
| 热启动到首次文字 | 516ms | 456ms |
| 冷启动场景结束到最终返回 | 96ms | 27ms |
| 热启动场景结束到最终返回 | 111ms | 28ms |

首次文字时间包含固定音频自身的前导区、模型上下文与计算；结束到返回包括已采入尾音的解码，不包含真实麦克风停止、JS桥及屏幕合成。该表只代表这组测试，不能换算成真人必然提速或零延迟。其他100ms投递场景最终收尾52～71ms，首字仍受音频自身静音影响。

原始模型与最终APK内优化模型的10.053秒固定音频流式结果逐字一致（51字符）；完整双路径回归三次均54字符、18次更新，约1.342～1.370秒完成离线快速投递识别，静音和取消通过。这些不是实时录音耗时或通用准确率结论。
